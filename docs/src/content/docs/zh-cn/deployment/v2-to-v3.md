---
title: 从 v2 SQLite 迁移到 v3
description: 使用 v3.0.22 升级 v2 SQLite 数据库，了解迁移边界及失败后的恢复方式。
---

原生 v3 服务会在打开 v3 存储前识别 v2 SQLite 数据库。原有启动命令可以继续使用 `--persistence db`、`--data-dir`、文件型 `--dsn sqlite://PATH?mode=rwc` 和 `--update-channel staging`。如果源数据库已加密，保留原有 `GPROXY_MASTER_KEY`，不要同时轮换主密钥。

## 升级前

- 保存当前 v2 可执行文件及启动配置。v2 自更新会替换可执行文件，不保留旧版；v3 数据库迁移无法找回已被替换的程序。
- 停止其他使用该数据库的实例。原生入口会在接触数据库前占用监听端口，迁移还需要 SQLite 独占锁。
- 预留完整源库备份、迁移工作库和独立切换快照所需的磁盘空间。
- 自动升级不支持 PostgreSQL、MySQL、远程 libSQL、v1 数据库或非标准 SQLite DSN。这些输入需要先显式导出、迁移。v2 PostgreSQL 到 v4 请使用[离线迁移工具](/zh-cn/deployment/v2-postgres-to-v4/)。

## 启动时的处理

1. 获取迁移锁，防止多个进程同时升级。
2. 在数据库旁创建私有目录 `gproxy-v2-backup-TIMESTAMP-PID`。
3. 独占锁定 SQLite，执行 WAL checkpoint，再将源库复制为备份目录中的 `gproxy-v2.db`。
4. 将支持的配置、可恢复的秘密、原始用量及上下游请求日志导入 `candidate/` 中的新 v3 数据库。
5. 校验导入数量、SQLite 完整性、引用关系、运行时控制状态、用量记录数及精确的历史结算费用总额。
6. 仅在校验通过后刷新数据并原子替换配置指向的数据库。保留备份和 `report.txt`；重新启动 v3 不会重复导入。

组织、团队和用户的通配路由授权（`*`）会保留。历史用量只迁移仍在 `usages` 中的明细，v3 据此重建小时聚合。v2 用量汇总、每日凭据统计和历史配额周期不导入，因此已被 v2 保留策略删除明细的历史不会出现在 v3 统计中；这些源表仍留在完整备份内。

凭据健康快照、tokenizer 缓存和 Codex 任务绑定不导入。`report.txt` 会列出每个非空但被跳过的表、记录数及原因。未知表（即使非空）和 v2 限流规则也会跳过并记录。不支持的特定路由授权、未知权限范围及主体已不存在的授权会跳过；支持的通配授权仍会导入。被跳过的策略在 v3 不会生效，需要升级后重新配置。

`downstream_requests` 和 `upstream_requests` 分别迁入 `request_logs` 和 `wire_logs`。请求 ID、时间、方法、路径或 URL、状态、请求头及请求/响应体会保留，包括同一请求的多次上游尝试。v2 状态码 0 变为未知响应状态。供应商和凭据引用会重新映射；已删除对象使用禁用的历史占位对象。日志按有界批次读写。

v2 特有的日志创建/更新时间和每次尝试的 `latency_ms` 没有对应的 v3 字段，仍保留在备份中；v3 从用量明细推导请求时长。审计日志不导入。浏览器和客户端可能需要重新登录；可恢复的 API key 会保留。

## 失败与回滚

替换前失败会保留原 v2 数据库。检查输出中的工作目录及数据库旁的 `.gproxy-v2-upgrade-blocked`。该标记防止进程管理器反复复制失败的数据库并耗尽磁盘。修复原因后，只删除这个标记再重试；不要通过删除备份重试。

回滚时停止 v3，保留当前 v3 数据库用于排查，重新安装已保存的 v2 可执行文件或相同的官方版本，再将备份 `gproxy-v2.db` 恢复到原数据库路径。恢复前，将当前 `-wal` 和 `-shm` 文件随当前数据库一起移开。恢复原启动配置和主密钥，再启动 v2。不要让 v2 打开已迁移的 v3 数据库。切换后写入的用量留在保存的 v3 数据库中，不会自动合并回 v2。
