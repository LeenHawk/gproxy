GPROXY 是基础设施。它站在每个客户端和每个 Provider 之间，所以它的设计目标就是成为
链路上你永远不用惦记的那一段。这一页用数字说明这意味着什么，并交代测试方法，
方便你对照自己的部署做判断。

## 核心数字

下面每个数字都是端到端的：请求先用用户密钥鉴权，经模型别名路由到 Provider 凭证，
发往上游，计价，再写入用量账本。没有为了让网关显得更快而关掉任何环节。

| 指标 | 结果 |
|---|---|
| 单连接下网关附加的延迟 | 中位数 0.21 ms，p99 0.50 ms |
| 计费吞吐，32 连接 | 27,000 请求/秒，p50 1.0 ms，p99 4.4 ms |
| 计费吞吐，256 连接 | 23,700 请求/秒，p99 26 ms |
| 计费吞吐，2,000 连接 | 22,900 请求/秒 |
| 仅鉴权与路由，不访问上游 | 108,000 请求/秒 |
| 10,000 并发连接，上游 500 ms | 18,600 请求/秒，中位数只比上游多 1.4 ms |
| 10,000 并发流，每条约 1.5 秒 | 6,300 流/秒，中位数只比上游多 15 ms |
| 20,000 并发连接，上游 500 ms | 18,500 请求/秒，零错误 |
| 10,000 个连接在线时的常驻内存 | 约 1.2 GB |
| 持续负载且无积压时的常驻内存 | 约 230 MB |

## 测试方法

- **机器。** 一台笔记本级别的主机：AMD Ryzen 7 8745H，16 线程，28 GB 内存，NVMe
  存储。压测客户端、网关和 mock 上游都跑在这台机器上，共用这些核心。网关独占一台
  机器时余量比这里显示的更大。
- **存储。** 默认的磁盘 SQLite 后端，WAL 模式，`synchronous=NORMAL`。没有 tmpfs，
  没有内存数据库。
- **上游。** 本机 mock，讲 OpenAI Chat Completions 线格式。测延迟的场景立即应答；
  测并发的场景每个响应延迟 500 ms，或者以 50 ms 间隔流式输出 20 个 chunk，
  模拟真实模型的行为。
- **负载。** `oha`，HTTP/1.1 长连接，每条连接一个在途请求，每轮 10 到 25 秒。
  每轮结束后都核对：数据库里的用量行数与上游收到的请求数一致。
- **对照。** 每个并发场景都直连 mock 再跑一次，绕过网关，把网关自身的贡献从
  压测工具和内核的开销里分离出来。

## 为什么快

- **请求路径上不碰数据库。** 控制面是内存快照，变更时原子替换。密钥、路由、凭证、
  价格和健康状态全部从内存解析，包括解密后的凭证本身。
- **零拷贝数据面。** 请求体以引用计数的字节块传递。流式响应除非协议转换必须改写，
  否则原样透传；一个请求体只在需要它的阶段解析一次。
- **结算在响应之后。** 用量行、汇总和健康观察在响应离开后才写入。积压有上界，
  突发流量不会让内存无限增长；队列满时响应路径等待，而不是丢弃。
- **批量提交。** SQLite 线程把已经排队的所有结算合并进一个事务。高负载下一批
  请求只付一次 WAL 提交的代价，而不是每个请求一次。正是这一点把上限从每秒几千
  笔结算推到了几万笔。
- **成对转换，没有中间格式。** OpenAI、Claude、Gemini 之间的转换是直接改写，
  不经过中间表示的两跳。

## 对你意味着什么

接上真实模型后，请求在 GPROXY 里的时间只是个零头。一次补全在上游要几百毫秒到
几十秒；网关在中位数上增加不到一毫秒，在尾部增加几毫秒。

吞吐也很少成为限制。单个实例每秒结算的请求数超过大多数部署一分钟的发送量；
到那个量级瓶颈是 SQLite 账本，多实例部署可以换成 PostgreSQL 或 MySQL。

需要调的是并发。原生宿主用 `GPROXY_MAX_IN_FLIGHT` 限制在途请求数，默认 1024。
把它提高到你预期的同时在途请求数，并确保进程能打开足够多的文件描述符：每个在途
请求占用一条客户端连接和一条到 Provider 的连接。每条打开的连接大约预留 110 KB
常驻内存。

## 复现

测试工具是一个 mock 上游、一个通过管理 API 创建 Provider、路由、用户和密钥的
种子脚本，以及一个 `oha` 运行脚本。任何 HTTP 压测工具都可以：带上 Bearer 密钥
打 `/v1/chat/completions`，结束后比较用量行数和请求数。两者若有差异，
那就是一个值得报告的 bug。
