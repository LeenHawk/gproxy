---
title: "Миграция PostgreSQL v2 на v4"
description: "Инструмент автономной миграции для перемещения базы данных PostgreSQL версии 2 в новую базу данных PostgreSQL версии 4."
---

Загрузите [Shell-скрипт](https://github.com/LeenHawk/gproxy/blob/main/scripts/migrate-v2-postgres.sh) и [вспомогательный Python-файл](https://github.com/LeenHawk/gproxy/blob/main/scripts/migrate-v2-postgres.py) из одной ревизии и сохраните оба файла в одном каталоге. Инструмент выполняет автономную миграцию схемы v2.3.2:

```text
v2 PostgreSQL -> temporary v2 SQLite -> v3.0.22 SQLite -> new v4 PostgreSQL
```

Исходный код PostgreSQL считывается за одну транзакцию повторяемого чтения, доступную только для чтения. Скрипт его не меняет. учётные данные остаются в снимке зашифрованными; существующие импортеры v3/v4 расшифровывают и повторно запечатывают их с помощью вашего мастер-ключа. Ни один из этих шагов не запускает сервер HTTP. Скрипт не загружает и не устанавливает двоичные файлы. Файл SQLite представляет собой обменный файл импорта, а не замену `pg_dump`: индексы PostgreSQL, значения по умолчанию и ограничения не воспроизводятся для восстановления.

<a id="download-and-requirements"></a>

## Скачать и требования

Сохраните скрипт локально перед его запуском:

```sh
curl -fL https://raw.githubusercontent.com/LeenHawk/gproxy/main/scripts/migrate-v2-postgres.sh -o migrate-v2-postgres.sh
curl -fL https://raw.githubusercontent.com/LeenHawk/gproxy/main/scripts/migrate-v2-postgres.py -o migrate-v2-postgres.py
```

- Bash, Python 3.10+ с SQLite и psycopg 3:

  ```sh
  python3 -m venv .migration-venv
  .migration-venv/bin/pip install 'psycopg[binary]>=3,<4'
  export PYTHON="$PWD/.migration-venv/bin/python"
  ```

- Исполняемый файл **v3.0.22** и текущая стабильная исполняемая версия v4 для вашей платформы. Загрузите/распакуйте их в отдельные каталоги из [v3.0.22](https://github.com/LeenHawk/gproxy/releases/tag/v3.0.22) и [стабильные выпуски](https://github.com/LeenHawk/gproxy/releases/latest). Исполняемый файл версии 4 должен включать поддержку PostgreSQL. Держите двоичный файл версии 3 закрепленным: этот мост предназначен для исходной схемы и синтаксиса команд. В официальной Linux версии 4.0.2 CLI отсутствует драйвер PostgreSQL; используйте текущую стабильную версию CLI (мост был проверен с версией 4.1.8).
- Полная резервная копия `pg_dump`, сделанная перед попыткой обновления, исходный мастер-ключ и достаточно места на локальном диске для обеих баз данных SQLite (включая журналы запросов). Импортер версии 3 загружает сведения об использовании в память, поэтому выделите объем памяти, пропорциональный сохраняемой истории использования.
- Новая выделенная пустая целевая база данных PostgreSQL, использующая схему `public`. Не запускайте GPROXY перед импортом. Импортер создает свои таблицы.

Остановите запись всех экземпляров GPROXY в исходный код перед окончательной подготовкой. Предпочитайте восстановить исходный дамп версии 2 во временную базу данных PostgreSQL и использовать для его чтения учётную запись SELECT-only. Если вы уже запустили версию 4 для старой базы данных, используйте исходную резервную копию, а не смешанную базу данных. Не отправляйте кому-либо свой дамп, учётные данные или мастер-ключ для запуска этого инструмента.

<a id="1-prepare-and-inspect"></a>

## 1. Подготовьте и осмотрите

Установите соединение URL и исходный base64 `GPROXY_MASTER_KEY` в вашей оболочке. Следующие запросы не записывают их в историю оболочки:

```sh
read -rsp 'Source PostgreSQL URL: ' GPROXY_V2_SOURCE_DSN; echo
export GPROXY_V2_SOURCE_DSN
read -rsp 'Original master key (empty if plaintext): ' GPROXY_MASTER_KEY; echo
export GPROXY_MASTER_KEY

# Optional if the v2 tables are outside public:
# export GPROXY_V2_SCHEMA=your_schema

bash migrate-v2-postgres.sh prepare ./migration-work /absolute/path/to/v3/gproxy
```

`migration-work` не должен существовать. Он создается с личными разрешениями, и весь вывод остается там. Команда копирует все исходные таблицы ограниченными пакетами, проверяет количество строк, добавляет недостающие поля старой схемы **только в SQLite**, затем запускает предварительную проверку v3, проверку импорта, целостности и использования. Legacy `image_price` сохраняется как цена за единицу `image_outputs` наряду с ценами токенов за миллион; он не переименовывается в цену токена.

Прежде чем продолжить, просмотрите эти файлы:

- `snapshot-report.json`: количество источников и временные корректировки схемы.
- `v3-preflight.log`, `v3-import.log`: результаты преобразования, пропущенные таблицы и изменения разрешений/маршрутов.
- `v3-verification.json`: количество конфигураций ядра и точная историческая стоимость.

Держите весь каталог в секрете. Он содержит копии баз данных и отчеты. Версия 3.0.22 принимает исходный ключ только через `--from-v2-master-key`, поэтому этот ключ на короткое время присутствует в аргументах процесса версии 3. Запустите подготовку на доверенной машине; не используйте трассировку оболочки (`bash -x`). Скрипт не печатает ключи.

<a id="2-import-into-a-new-postgresql-database"></a>

## 2. Импортируйте в новую базу данных PostgreSQL.

Сохраните тот же мастер-ключ и подготовленный каталог:

```sh
read -rsp 'New empty target PostgreSQL URL: ' GPROXY_V4_TARGET_DSN; echo
export GPROXY_V4_TARGET_DSN

bash migrate-v2-postgres.sh import ./migration-work /absolute/path/to/v4/gproxy
```

Сценарий проверяет отпечаток ключа и отклоняет непустую цель перед вызовом v4. Он импортирует конфигурацию, идентификацию и использование через `import --from-v3`, затем проверяет импортированные идентификаторы основных объектов, хэши паролей, дайджесты ключей API, счетчик использования, исходные идентификаторы запросов и затраты (включая округленные сохраненные суммы в версии 4). Обзор `v4-import.log` и `v4-verification.json`. Неподдерживаемые провайдеры не выполняют явный импорт; сценарий не позволяет их молча пропускать.

Только после просмотра отчетов направьте развертывание версии 4 на новую базу данных с тем же мастер-ключом. Прежде чем возобновить трафик, проверьте существующий логин, доступ к ключу API, учётные данные провайдера, маршруты, разрешения и историю использования. Не запускайте оба развертывания с использованием одних и тех же токенов обновления OAuth.

<a id="what-the-bridge-preserves-and-what-it-does-not"></a>

## Что мост сохраняет, а что нет

Мост наследует существующие правила миграции; он не обещает идентичного поведения для каждой функции версии 2. Через эти правила проходят провайдеры, учётные данные, маршруты, пользователи, восстанавливаемые ключи API, хэши паролей и сохраняемые сведения об использовании. См. [с v2 по v3](/ru/deployment/v2-to-v3/) и [с v3 по v4](/ru/deployment/v3-to-v4/) для границ преобразования.

- В v4 раундах денежные значения сохраняются с точностью до 9 знаков после запятой. Точные первоначальные затраты на использование остаются в `metrics.v3.cost`; проверка сравнивает эти оригиналы.
- Удаленные сведения об использовании невозможно восстановить из старых агрегатов. Сводные данные об использовании версии 2 и исторические циклы квот сохраняются в моментальном снимке, а не импортируются.
- Журналы запросов попадают во временную базу данных версии 3, но не становятся записями версии 4. Сеансы, журналы аудита, работоспособность учётных данных и кэши не переносятся.
- Разрешения Some, лимиты запросов, перезаписи и настройки провайдера изменяются или не могут быть переведены. Прежде чем обслуживать трафик, прочитайте оба отчета о миграции и заново создайте необходимые политики. Прохождение проверок количества не является доказательством эквивалентности политики.

<a id="failure-retry-and-rollback"></a>

## Сбой, повторная попытка и откат

Неудачная команда завершает работу, не нулевую, и сохраняет все рабочие файлы. Он никогда не удаляет базу данных и не пытается отменить частичный импорт. Для `prepare` не требуется целевое соединение, и исходный код никогда не записывается ни на одном этапе.

Если подготовка не удалась, просмотрите отчеты, устраните указанную причину и подготовьтесь к переходу в **новый рабочий каталог**. Если импорт не удался, сохраните частично заполненную цель и ее журналы для диагностики. Устранив причину, используйте **новую пустую цель и новый рабочий каталог** для еще одного полного запуска. Повторное использование заполненной цели намеренно запрещено; не используйте `--merge` для обхода этой проверки.

Перед переключением откат означает сохранение исходного развертывания и базы данных. После переключения остановите версию 4 и восстановите исходное развертывание/резервную копию версии 2; использование, записанное в v4, не объединяется обратно автоматически. Сохраняйте исходный дамп и рабочий каталог до тех пор, пока миграция не будет проверена и ваша политика резервного копирования не разрешит их удаление.
