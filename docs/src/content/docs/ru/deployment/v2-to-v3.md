---
title: Миграция SQLite с v2 на v3
description: Обновление базы SQLite v2 с помощью v3.0.22, ограничения миграции и восстановление исходной базы.
---

Нативный сервер v3 распознаёт базу SQLite v2 до открытия хранилища v3. В прежней команде запуска можно оставить `--persistence db`, `--data-dir`, файловый `--dsn sqlite://PATH?mode=rwc` и `--update-channel staging`. Если исходная база зашифрована, сохраните прежний `GPROXY_MASTER_KEY`. Не совмещайте обновление с ротацией мастер-ключа.

## Перед обновлением

- Сохраните установленный исполняемый файл v2 и параметры запуска. Самообновление v2 заменяет файл без сохранения прежней версии; миграция v3 не может восстановить уже удалённую программу.
- Остановите остальные процессы и экземпляры, использующие базу. Нативный сервер резервирует порт прослушивания до обращения к базе; миграции также нужна исключительная блокировка SQLite.
- Освободите место для полной резервной копии, рабочей базы миграции и отдельного снимка для переключения.
- PostgreSQL, MySQL, удалённый libSQL, базы v1 и нестандартные SQLite DSN не поддерживают автоматическое обновление. Сначала выполните явный экспорт или миграцию. Для полной миграции с v2 на v4 используйте [автономный инструмент миграции](/ru/deployment/v2-to-v4/).

## Что происходит при запуске

1. Устанавливается блокировка миграции, чтобы базу обновлял только один процесс.
2. Рядом с базой создаётся закрытый каталог `gproxy-v2-backup-TIMESTAMP-PID`.
3. SQLite блокируется монопольно, выполняется WAL checkpoint, затем исходная база копируется в `gproxy-v2.db` в каталоге резервной копии.
4. Поддерживаемая конфигурация, восстанавливаемые секреты, исходные записи использования и журналы запросов клиентов и провайдеров импортируются в новую базу v3 в `candidate/`.
5. Проверяются количество импортированных записей, целостность SQLite, ссылки, состояние управления, число записей использования и точная сумма исторических расходов.
6. Только после успешной проверки данные записываются на диск и настроенная база заменяется атомарно. Сохраните резервную копию и `report.txt`; повторный запуск v3 не повторяет импорт.

Универсальные разрешения маршрутов (`*`) для организаций, команд и пользователей сохраняются. Из исторического использования переносятся только оставшиеся подробные записи `usages`; v3 заново строит по ним почасовые агрегаты. Сводки использования v2, ежедневная статистика учётных данных и исторические циклы квот не импортируются. История, чьи подробные записи уже удалены политикой хранения v2, не появится в статистике v3. Исходные таблицы остаются в полной резервной копии v2.

Снимки работоспособности учётных данных, кэш токенизатора и привязки задач Codex не импортируются. В `report.txt` перечисляются все пропущенные непустые таблицы, число записей и причины пропуска. Неизвестные таблицы, даже непустые, и правила лимитов запросов v2 также пропускаются с записью в отчёт. Не переносятся неподдерживаемые разрешения отдельных маршрутов, неизвестные области разрешений и разрешения удалённых субъектов; поддерживаемые универсальные разрешения импортируются. Пропущенные политики не действуют в v3 — настройте их заново после обновления.

`downstream_requests` и `upstream_requests` переносятся соответственно в `request_logs` и `wire_logs`. Сохраняются ID запросов, время, методы, пути или URL, статусы, заголовки запросов и тела запросов/ответов, включая несколько обращений к провайдерам для одного запроса. Статус 0 в v2 становится неизвестным статусом ответа. Ссылки на провайдеров и учётные данные переназначаются; для удалённых объектов создаются отключённые исторические записи. Журналы читаются и записываются ограниченными пакетами.

Специфичные для v2 время создания/обновления журналов и `latency_ms` каждой попытки не имеют соответствующих полей в v3 и остаются в резервной копии. v3 вычисляет длительность запросов по данным использования. Журналы аудита не импортируются. Браузерные и клиентские сеансы могут потребовать повторного входа; восстанавливаемые ключи API сохраняются.

## Ошибки и откат

Ошибка до замены оставляет базу v2 на месте. Проверьте указанный рабочий каталог и файл `.gproxy-v2-upgrade-blocked` рядом с базой. Этот маркер предотвращает повторное копирование проблемной базы процессным менеджером и заполнение диска. Устраните причину и удалите **только маркер**, чтобы повторить попытку. Не удаляйте резервную копию ради повторного запуска.

Для отката остановите v3, сохраните текущую базу v3 для диагностики, установите сохранённый исполняемый файл v2 или тот же официальный выпуск и восстановите резервный `gproxy-v2.db` по исходному пути. Перед восстановлением перенесите текущие файлы `-wal` и `-shm` вместе с текущей базой. Восстановите прежние параметры запуска и мастер-ключ, затем запустите v2. Не открывайте в v2 уже мигрированную базу v3. Данные использования после переключения остаются в сохранённой базе v3 и не переносятся обратно автоматически.
