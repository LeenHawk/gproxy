Используйте имя пользователя и пароль для входа в консоль, а также ключ API шлюза для вызова моделей. Учётные данные аутентификации провайдера принадлежат провайдерам и не могут выполнить вход в GPROXY.

<a id="first-administrator"></a>

## Первый администратор

Приложение создает администратора в мастере первого запуска. CLI создает администратора в пустом экземпляре и печатает сгенерированный пароль и ключ API. Вместо этого вы можете указать начальные значения:

```sh
export GPROXY_ADMIN_USER='admin'
export GPROXY_ADMIN_PASSWORD='your-initial-password'
export GPROXY_BOOTSTRAP_ADMIN_API_KEY='your-initial-gateway-key'
./gproxy serve
```

В новом экземпляре пароль и ключ генерируются, если они опущены. **Явный `GPROXY_ADMIN_PASSWORD` также обновляет пароль пользователя с тем же именем или восстанавливает и переименовывает администратора `0`, если при перезапуске ни одно имя не совпадает; опция ключа API запускается только при первом запуске.** `GPROXY_BOOTSTRAP_CHANNELS` больше не создает провайдеров; добавьте провайдеров в консоли.

CLI / Пользователи контейнера входят в систему на `/console/`. Персональные страницы и страницы управления используют файл cookie сеанса `gproxy_session` HTTP, срок жизни которого настраивается `session_ttl_secs`. Приложение использует консоль внутри приложения.

<a id="users-organizations-and-teams"></a>

## Пользователи, организации и команды

Администраторы экземпляра создают пользователей с контролем доступа. Роль пользователя — `admin` или `user`. Пользователь без пароля не может войти в систему, но может использовать выданные ключи API с соответствующими разрешениями.

Членство в организации и команде назначает пользователей и определенные роли управления. Ключ API может быть привязан к организации или команде; эта привязка определяет видимость учётных данных и применимые бюджеты. Заголовки запросов не могут переопределить привязку.

Администраторы организации и группы управляют только функциями, доступными в их области. Они не являются администраторами экземпляров. См. [Консольное и ограниченное администрирование](/ru/guides/console/).

<a id="create-a-key"></a>

## Создать ключ

Управляйте личными ключами в разделе **Мой аккаунт → Ключи**. Администраторы экземпляра также могут использовать **Контроль доступа → Пользовательские ключи**.

| Параметр | Значение |
| --- | --- |
| Имя | Определите приложение или устройство с помощью ключа |
| Право собственности | Пользователь и дополнительная организация или команда |
| Срок действия и включенное состояние | Ключи с истекшим сроком действия или отключенные ключи не могут отправлять новые запросы |
| Управление | Разрешать операции управления в зависимости от разрешений пользователя и области действия; выключен по умолчанию |
| Сохранять секрет | Позвольте полной стоимости раскрыться позже; выключен по умолчанию |
| Бюджет затрат | Администраторы могут установить фильтр по сумме, периоду и модели |

Скопируйте полный ключ при его создании. Ключ без сохраненного секретного материала, включая импорт только для дайджеста, не может быть раскрыт позже. Для раскрытия сохраненных ключей по-прежнему требуется разрешение.

Первоначальный бюджет и ключ можно сохранить вместе. Неудачная проверка бюджета не создает ключ отдельно.

<a id="rotate-or-revoke"></a>

## Повернуть или отменить

Клавиши поддерживают вращение. Старое значение становится недействительным, поэтому обновите конфигурацию клиента. Для постепенной миграции клиентов создайте второй ключ и отключите или удалите старый после переключения всех клиентов.

Управление операциями API:

- `POST /admin/api/api-keys/{id}/rotate`: повернуть клавишу.
- `GET /admin/api/api-keys/{id}/secret`: раскрыть секрет.
- Персональными эквивалентами API являются `/portal/api/keys/{id}/rotate` и `/portal/api/keys/{id}/secret`.

Отзыв вступает в силу немедленно на экземпляре, который его записал. Другие экземпляры многоэкземплярного развертывания отвечают на аутентификацию из своего моментального снимка в памяти и перестают принимать ключ при перезагрузке: в течение миллисекунд из-за аннулирования общего кэша и самое позднее после 30-секундного опроса редакций, если это сообщение потеряно. См. [Архитектура](/ru/introduction/architecture/).

Удаление участника из организации или команды отключает привязанные к нему ключи этого пользователя, включая внутренние ключи OAuth, в той же транзакции.

<a id="send-a-key"></a>

## Отправить ключ

```text
Authorization: Bearer <gateway-key>
x-api-key: <gateway-key>
x-goog-api-key: <gateway-key>
```

Используйте обычный для клиентского протокола заголовок, не указывая конфликтующих ключей. Для доступа к управлению API требуется флаг управления ключом; Обычный ключ вывода администратора не получает автоматически доступ к управлению.

<a id="oauth-sessions"></a>

## Сеансы OAuth

GPROXY может выдавать токены доступа после авторизации пользователя. Внутренние ключи OAuth отличаются от обычных ключей пользователя и не могут быть созданы или раскрыты как обычные ключи носителя. Авторизованные сеансы можно отменить в консоли.

См. [CLI клиенты](/ru/guides/cli-clients/) для настройки клиента и потоков авторизации.
