Интерфейсы командной строки провайдера Some взаимодействуют не только с конечной точкой вывода. Они извлекают профили учётных записей, окна использования, плагины, задачи и файлы из плоскости управления провайдера и отказываются работать без них.

Таким образом, канал может объявить **таблицу маршрутов служб**: известные ему пути плоскости управления и то, что каждый из них возвращает. Хост сопоставляет входящий путь с этой таблицей, прежде чем он попытается перейти на плоскость данных.

<a id="reaching-them"></a>

## Достичь их

Путь плоскости управления зависит от провайдера, поэтому он сопоставляется только при монтировании **провайдера или пространства имен**. Для сопоставления маршрута службы требуется канал, а для агрегированных имен монтирования его нет.

```text
https://gproxy.example/codex/backend-api/wham/profiles/me
                       ^^^^^ the provider (or namespace) named "codex"
```

<a id="the-three-views"></a>

## Три взгляда

`x-gproxy-view` называет то, что клиент API хочет вернуть. Отсутствие означает `caller`, и это единственное представление, которое может запросить обычный участник.

| Заголовок | Что он отвечает |
| --- | --- |
| `x-gproxy-view: caller` | **Факты об этом клиенте API** — его окна использования, его бюджетная цепочка, ресурсы, созданные его собственными вызовами. К провайдеру никогда не обращаются по поводу личности, использования или настроек. |
| `x-gproxy-view: pool` | То же самое, агрегировано по всем учётным данным аутентификации в цели. |
| `x-gproxy-view: credential:{id}` | Сырой. Собственная аутентификация указанных учётных данных передается провайдеру, и ответ провайдера возвращается нетронутым. |

Кто что может просить, решает право собственности, а не флаг. Целью являются **видимые** учётные данные клиента API этого провайдера — тот же набор, который может потратить вызов модели с тем же ключом — и клиент API является его администратором только в том случае, если он является администратором экземпляра или членом `Admin` организации или команды, которая владеет **каждыми** учётными данными в этом наборе. Все остальное является членством, и участник может запросить только `caller`; `pool` и `credential:{id}` — это `403`.

«Каждые учётные данные» не являются формальностью: администрирование одной организации не должно создавать пул, который также содержит пул другой организации. По своей конструкции бесхозные учётные данные не имеют администратора — никто не является ничьим администратором — поэтому в однопользовательском экземпляре, где все учётные данные являются общими, только администратор экземпляра достигает `pool` и `credential`.

**В создании ключей отказано при каждом представлении.** Долгосрочный ключ API в общей подписке — это именно те учётные данные, которые существуют в объединенном шлюзе, чтобы избежать раздачи.

Путь, неизвестный таблице, — `404`, если только представление не `credential:{id}`.

<a id="what-is-not-metered"></a>

## Что не измеряется

Вызов службы провайдера требует **аренды без лимиты запросов** — взимание платы за окно для выборки профиля приведет к расходованию квоты, необходимой клиенту API для трафика, который стоит денег — и записывает **нет записи захвата**. Движок не записывает записи провайдера для службы, поэтому клиенту не на что будет ссылаться, и он будет восприниматься как запрос, который не достиг ни одного провайдера.

Он проходит цепочку бюджета, поскольку представление `caller` визуализирует из него собственные окна API-клиента. Сообщение о квоте не означает ее расходование.

Вызовы служб содержат тот же токен отмены, что и запросы модели. Отмена останавливает подготовку учётных данных, отправку провайдеру и потоковую передачу ответов HTTP. Для служб WebSocket это означает рукопожатие; хост управляет установленным сокетом. Сервисы по-прежнему не требуют аренды с ограничением скорости и не требуют использования модели.

## Codex CLI

Канал `codex` объявляет внутренние вызовы ChatGPT, которые CLI выполняет помимо ответов. Факты о телепередачах взяты из собственного источника CLI под `samples/codex`:

| Семья | Пути |
| --- | --- |
| плагины и MCP | `/backend-api/ps/**` |
| учётная запись, настройки, использование, задачи, среды, удаленное управление | `/backend-api/wham/**` |
| загружает | `/backend-api/files/**` |
| общий доступ к плагину рабочей области | `/backend-api/public/plugins/**` |
| проверка личности стартапа | `GET /v1/user-auth-credential/whoami` |

CLI обращается к одним и тем же конечным точкам двумя способами — `/backend-api/wham/**` на хостах ChatGPT и `/api/codex/**` на хостах Codex API. Оба написания, а также голые монтирования `/codex/**` и `/ps/**` нормализуются на `/backend-api/**` до обращения к таблице, поэтому выбор клиентом стиля хоста не является вопросом конфигурации.

`/backend-api/wham/remote/control/server` — это **WebSocket**, и это единственный маршрут службы, который обновляется. Codex категорически отказывается от синтезированного представления, поэтому `x-gproxy-view: credential:{id}` от администратора этих учётных данных является единственным способом пройти.

Все, что не классифицируется в таблице, попадает в строки префикса `/backend-api/{*path}` и пересылается как есть, включая ответы, отличные от 2xx.

## Claude Code

Канал `claudecode` объявляет вызовы `/api/**` с областью действия OAuth, которые CLI выполняет помимо сообщений: профиль, проверка, роли, начальная загрузка, использование, ограничения политики, настройки учётной записи, загрузка и скачивание файлов, организационные соединители, плагины и навыки, элементы управления подключением и выставлением счетов, перенаправление обновлений рабочего стола и поверхность дизайна Claude.

Все они разрешаются против `api.anthropic.com`; `claude.ai` обслуживает только вход в систему с использованием файлов cookie, поэтому канал здесь не обращается к нему.

В `caller` и `pool` ответы об идентификации, использовании и настройках синтезируются на основе того, что знает этот экземпляр, а их идентификаторы представляют собой стабильный хэш идентификатора провайдера и клиента API. Ничего об общей учётной записи не выдумано и ничего о ней не утекает: учётная запись, организация и план, отображаемые CLI, являются синтетическими значениями GPROXY, а не учётной записи провайдера.

<a id="gproxy-as-the-oauth-issuer"></a>

## GPROXY как эмитент OAuth

CLI, который входит в систему с помощью OAuth, может войти в **этот экземпляр** вместо провайдера. Это отличается от `login()` SDK, который использует чужой OAuth в качестве клиента:

```text
  Claude Code ──authorize/token──▶ gproxy   (the authorization server)
                                     │
                                     └──login()──▶ OpenAI   (the client)
```

Конечные точки располагаются под каждым монтированием, поэтому клиент обнаруживает, с кем он разговаривает:

```text
GET  {mount}/v1/oauth/authorize
POST {mount}/v1/oauth/authorize
POST {mount}/v1/oauth/token
POST {mount}/v1/oauth/device/code
POST {mount}/v1/oauth/revoke
GET  {mount}/v1/.well-known/oauth-authorization-server
GET  /.well-known/oauth-authorization-server{mount}/v1
```

```sh
curl -s http://127.0.0.1:8787/v1/.well-known/oauth-authorization-server
```

```json
{"issuer":"http://127.0.0.1:8787/v1",
 "authorization_endpoint":"http://127.0.0.1:8787/v1/oauth/authorize",
 "token_endpoint":"http://127.0.0.1:8787/v1/oauth/token",
 "device_authorization_endpoint":"http://127.0.0.1:8787/v1/oauth/device/code",
 "revocation_endpoint":"http://127.0.0.1:8787/v1/oauth/revoke",
 "response_types_supported":["code"],
 "grant_types_supported":["authorization_code","refresh_token",
   "urn:ietf:params:oauth:grant-type:device_code"],
 "code_challenge_methods_supported":["S256"]}
```

v3 обслуживал их в корне; v4 переместил их в `/v1`, поэтому правило префикса такое же, как и `/v1/messages`, и существует одна его реализация.

<a id="rules-this-issuer-does-not-bend"></a>

### Правила, которые этот эмитент не нарушает

- **PKCE S256, всегда.** `plain` отклоняется и поэтому является отсутствующим вызовом. Каждый зарегистрированный клиент является общедоступным, без каких-либо секретов, которые нужно доказать, поэтому верификатор — единственное, что стоит между утекшим кодом и токеном.
- **URI перенаправления точно совпадают.** Не префикс, не подстановочный знак, не «того же происхождения». Каждое более слабое правило принимает URL, которым управляет злоумышленник.
- **Коды, токены обновления и коды устройств являются одноразовыми**, используются и заменяются одним атомарным пакетом, поэтому два погашения не могут быть успешными одновременно, даже если они чередуются.
- **Воспроизведение кода или токена обновления аннулирует всю семью** — грант, его внутренний ключ и каждый когда-либо выпущенный токен. Невозможно отличить потерянный ответ от украденных учётных данных, поэтому предполагается утечка. Законный клиент повторно выполняет вход в систему; вор не может. Поток устройства является исключением, поскольку клиент опроса по своей природе повторно отправляет свой код.

<a id="what-an-oauth-caller-may-do"></a>

### Что может делать клиент OAuth API

Токен доступа — это учётные данные, которые пользователь передал **чужому двоичному файлу**. Если клиент не указан в `oauth.cliClientIds` экземпляра, он может только перечислять модели, получать модель, подсчитывать токены, генерировать, передавать в потоковом режиме и сжимать. Все остальное — это `403`, и это ограничение применимо и к учётной записи администратора экземпляра — учётная запись администратора — это именно та учётная запись, в которой сторонний токен не должен становиться учётными данными административной аутентификации.

Присвоение имени клиенту в `cliClientIds` означает признание того, что он говорит от имени пользователя во всем API.

Клиент OAuth API также не может создавать, ротировать, раскрывать или удалять ключи, а также не может изменять пароль учётной записи.

<a id="session-affinity"></a>

## Привязка сеанса

Многооборотный CLI работает лучше всего, когда один разговор ведется по одним учётным данным аутентификации. GPROXY считывает идентификатор диалога от клиента, который **фактически отправил** запрос, а не от провайдера, которому он будет перенаправлен — запрос кода Claude, перенаправленный на другой канал, по-прежнему считывает поле Claude Code.

Лестница, первая непустая, побеждает:

1. `x-gproxy-session-id`, собственный заголовок шлюза;
2. `thread-id`, `session-id`, `x-claude-code-session-id`, `x-conversation-id`,
   `x-grok-session-id`;
3. собственное поле входящего тела — `client_metadata.thread_id`/`session_id` для ответов, `session_id` для Claude *внутри* JSON-encoded `metadata.user_id`, `request.session_id` и `request.sessionId` для Gemini;
4. отпечаток sha256 стабильного префикса диалога;
5. идентификатор запроса, честно помеченный как резервный, а не заявленный как сеанс.

Ничто не повторяется через произвольный JSON в поисках поля с именем `session_id`, а идентификаторы запроса, поворота и кэша — `x-grok-req-id`, `user_prompt_id`, `prompt_cache_key`, `previous_response_id` — не являются **никогда** сеансами.

Заголовок шлюза удаляется до того, как запрос передается провайдеру, а также удаляется из запроса клиента: клиент не должен иметь возможность выбрать диалог другого клиента API, отправив заголовок, который шлюз использует для его имени. Отсутствующий заголовок сеанса никогда не отклоняет запрос.
