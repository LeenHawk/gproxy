Разрешения контролируют доступ, лимиты запросов контролируют частоту запросов, а бюджеты затрат контролируют расходы. Эти проверки являются отдельными.

<a id="permissions"></a>

## Разрешения

Правило разрешений принадлежит пользователю или ключу API и может фильтроваться по провайдеру, шаблону модели и операции. Шаблоны моделей поддерживают `*` и `?`, поэтому ограничения модели не требуют отдельных провайдеров.

Правила упорядочены по убыванию приоритета, затем ID. Первое правило сопоставления предоставляет решение `allow` или `deny`. Обычным пользователям необходимо применимое разрешающее правило. Администраторы экземпляров обходят обычные правила разрешений, в то время как токены доступа OAuth по-прежнему ограничены фиксированными базовыми показателями операций (каталог моделей, подсчет токенов, генерация, потоковая передача, сжатие), если только клиент не указан в `oauth.cli_client_ids`.

Для каждой операции также требуется точная область действия `gproxy:<operation>` с использованием идентификаторов операций Snake_case (например, `gproxy:list_models`, `gproxy:generate_content` и `gproxy:stream_generate_content`). Для услуг провайдера требуется `gproxy:services` и настроенный клиент CLI. Ни администратор, ни запись белого списка CLI не обходят проверку области. Пустые области, `openid` и `profile` не предоставляют доступа к ресурсам; существующие клиенты должны запросить необходимые области и авторизоваться повторно. Области никогда не переопределяют базовые или обычные правила разрешений.

| Поле API | Значение |
| --- | --- |
| `userId` / `apiKeyId` | Ровно один предмет правила |
| `providerId` | Необязательный; опустить, чтобы сопоставить всех провайдеров |
| `modelPattern` | Шаблон модели, по умолчанию `*` |
| `operation` | Необязательный; опустить, чтобы сопоставить все операции |
| `action` | `allow` или `deny` |
| `priority` | Более высокие значения соответствуют первым |

Поле `permitted` каталога моделей сообщает о доступе клиента API. Недоступная модель все равно может появиться в каталоге.

<a id="credential-visibility"></a>

## видимость учётных данных

Одного разрешения недостаточно: клиенту API также необходимы доступные учётные данные. Владение учётными данными и привязки пользователя, организации и группы ключа API определяют видимость. Область управления, разрешение модели и владение учётными данными — это отдельные настройки.

Маршруты обслуживания провайдера (учётная запись, использование и другие немодельные конечные точки, объявленные каналом) не имеют модели или операции, поэтому только правило, охватывающее всего провайдера (любая модель, без операции), разрешает или запрещает их. Они находятся за пределами базовой линии операции OAuth.

<a id="rate-limits"></a>

## Лимиты запросов

Ограничения скорости пользователя или ключа API- указывают метрику, предел, период в секундах, дополнительный шаблон модели и включенное состояние. Распространенными метриками являются `requests` и `concurrency`. Текущие счетчики используют серверную часть кэша; нескольким экземплярам требуется общее состояние кэша.

Проверки разрешений выполняются до учета лимиты запросов. Просмотрите ошибку и журналы, чтобы отличить ограничения клиента API от ограничений учётных данных проверки подлинности провайдера.

<a id="cost-budgets"></a>

## Бюджеты затрат

Бюджеты могут принадлежать пользователям, ключам API, организациям и командам в USD. Запросы проверяют ключевой и пользовательский бюджеты, а также фактическую организацию ключа и привязки команды. Материнская организация команды не обвиняется только потому, что существуют такие отношения.

Каждый применимый включенный бюджет должен иметь оставшуюся емкость. Фильтры периодов и моделей настраиваются в консоли. Фактическая стоимость рассчитывается после звонка провайдеру, поэтому текущие и одновременные вызовы могут превысить лимит. Бюджет не является жестким ограничением расходов провайдеров услуг.

Отсутствующие цены влияют на общую стоимость и потребление бюджета. Проверьте также [Цены](/ru/reference/pricing/). В суммах бюджета в API используются десятичные строки.

<a id="provider-and-credential-limits"></a>

## Ограничения учётных данных провайдера и аутентификации

Ограничения провайдера по умолчанию применяются отдельно к каждому учётным данным аутентификации, а не к одному общему пулу провайдеров. Включенное правило учётных данных с тем же именем переопределяет правило провайдера по умолчанию. Восстановление наследования удаляет отдельную конфигурацию.

Локальные лимиты отличаются от разрешений учётной записи провайдера. Сброс локального правила не сбрасывает баланс или окно провайдера. См. [Провайдеры и учётные данные](/ru/guides/providers/) и [Консоль](/ru/guides/console/).

<a id="diagnose-a-rejection"></a>

## Диагностика отказа

- `401`: проверьте достоверность ключа и пользователя.
- `403`: проверьте разрешения, видимость учётных данных, области OAuth и базовые показатели операции OAuth.
- `429`: проверьте лимиты запросов клиента API, бюджеты, ограничения локальных учётных данных и квоты провайдера.

Проверьте соответствующего пользователя, ключ и учётные данные в консоли, затем используйте конкретную зарегистрированную ошибку, чтобы определить ограничивающее правило.
