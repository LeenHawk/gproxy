**Канал** — это встроенный адаптер для одного семейства провайдеров. **Провайдер** — это одно сохраненное соединение в канале: имя, необязательный базовый URL, собственный `config` JSON канала и пул учётных данных. Создайте столько провайдеров для каждого канала, сколько вам нужно — `openai-main` и `openai-eu` могут находиться на канале `openai`.

Каждая запись здесь представляет собой одну транзакцию с изменением версии конфигурации, и экземпляр перезагружается до того, как уведомит свои одноранговые узлы, поэтому изменение применяется к следующему запросу без перезапуска.

<a id="vendors-that-need-no-channel"></a>

### Провайдеры, которым не нужен канал

Канал — это код, который необходимо поддерживать в отношении протокола провайдера, и провайдер получает его только в том случае, если строка провайдера не может указать, что ему нужно. Провайдер, вся разница которого состоит в источнике и заголовке, является провайдером `custom`:

```json
{ "name": "example-vendor", "channel": "custom",
  "baseUrl": "https://api.example-vendor.com",
  "config": { "dialects": ["openai_chat"] } }
```

Раньше таким же образом обслуживались шлюзы NVIDIA NIM, Vercel AI и шлюз Cloudflare AI; у каждого теперь есть канал, поскольку обычной конфигурации провайдера для них недостаточно.

<a id="provider-configuration"></a>

## Конфигурация провайдера

| Поле | Значение |
| --- | --- |
| `name` | Ярлык оператора, уникальный. Это также **префикс провайдера** и левая половина формы `provider/model`. |
| `channel` | Один из идентификаторов выше. |
| `baseUrl` | Базовый адрес, если канал поддерживает его настройку. |
| `config` | Собственный канал JSON. Каждый канал объявляет, какие ключи он принимает; `GET /admin/api/channels` — это список. |
| `connectionProfileId` | Исходящий стек — прокси, эмуляция TLS — принимают вызовы этого провайдера. |
| `enabled` | Отключённый провайдер исключается из выбора. |

`config` для `custom` содержит `dialects` (какой форматы поддерживает конечную точку), статические `headers`, `allowed_headers` и два переключателя магического кэша. Каналы, выдающие себя за провайдера CLI, объявляют свои собственные идентификационные заголовки и защищают их от того, что клиент может подделать.

<a id="claude-model-fallback"></a>

### Резервная модель Claude

Установите для `fallback_mode` значение `off` (по умолчанию), `default` или `models`, при этом `fallback_models` содержит упорядоченный список идентификаторов моделей провайдеров. Консоль отображает эти поля из дескриптора канала. Списки пропускают пробелы, дубликаты и основную модель и используют не более трех резервных моделей.

- **Конечные точки Claude API, Claude Code и Custom Claude:** отправьте `fallbacks` от Anthropic и соответствующий заголовок бета-версии. Делегаты режима по умолчанию в Anthropic.
- **OpenRouter:** отправьте `fallbacks` для сообщений Claude или `models` для завершения чата. OpenRouter выполняет откат модели. Это не меняет `provider.allow_fallbacks`, который управляет маршрутизацией провайдеров для той же модели. Существующий клиент `fallbacks` или `models` имеет приоритет. Запросам ответов не предоставляется недокументированный резервный параметр.
- **Vercel, Azure, Vertex и AWS Bedrock:** GProxy повторяет Claude `refusal` на следующей настроенной модели, используя те же учётные данные, с новой подготовкой и подписанием канала. В режиме по умолчанию в пространстве имен основной модели выбирается `claude-opus-4-8`. Для идентификаторов, специфичных для облака, настройте полные идентификаторы, принимаемые этим провайдером.

Резервный вариант шлюза также применяется после преобразования протокола в Claude. Он не повторяет произвольные ошибки HTTP. Потоковое содержимое доставляется немедленно; после вывода для продолжения требуется кредит провайдера с требованием предварительного заполнения. Серверный инструмент никогда не воспроизводится повторно без погашаемого кредита. Каждая физическая попытка рассматривается отдельно и оценивается в соответствии с ее моделью; отказ в сообщении о нулевой выработке не подлежит оплате. В окончательном ответе сохраняется использование верхнего уровня последней попытки.

<a id="claude-code-usage-limit-modes"></a>

### Claude Code режимы ограничения использования

Оба переключателя каналов по умолчанию установлены на `false`:

- `low_priority: true` принимает предложение с более низким приоритетом, предоставленное сервером, после отклонения пятичасового лимита. Затем сеанс отправляет `anthropic-usage-limit: slow` до тех пор, пока это окно не будет сброшено или сервер не выйдет из режима. Недельные лимиты и отдельная надбавка с более низким приоритетом по-прежнему применяются.
- `extended_usage: true` отправляет `anthropic-usage-limit: extended` для продолжения результатов инструмента, когда не известно, что платное дополнительное использование включено. Сервер решает, доступна ли льгота; он не сбрасывает квоту подписки.

Явный клиентский заголовок `slow` или `extended` поддерживается даже при выключенных обоих переключателях; эти два значения являются взаимоисключающими. CountTokens и запросы управления не содержат этот заголовок. Для других клиентов сообщения о результатах инструмента предоставляют сигнал продолжения; частные флаги глубины задачи CLI и эксперимента недоступны шлюзу.

При отправке `slow` GProxy ожидает `429 slot_busy` и перегружает ответы, а затем повторяет тот же буферизованный запрос с теми же учётными данными. Как и в CLI 2.1.302, задержка по умолчанию составляет 20 секунд с джиттером 30 %, а максимальное время ожидания по умолчанию составляет 20 минут; подсказки сервера ограничены 5–600 секундами на задержку и общей продолжительностью 1–360 минут. Крайний срок хоста и отмена могут остановить ожидание раньше. Отказы в бюджете, еженедельном лимите и приемлемости возвращаются без этой повторной попытки, а потоки успешных ответов, невоспроизводимые тела и непрозрачные погашения резервных кредитов никогда не воспроизводятся.

В представлении квот также фиксируются зарегистрированные льготы с более низким приоритетом и льготы. Они не блокируют нормальный трафик. Явные режимы исключают только соответствующие отчетные окна подписки для этого запроса; местные бюджеты, ограничения модели и время восстановления сбоя провайдера/лимиты запросов по-прежнему применяются.

<a id="per-operation-url-overrides"></a>

### Переопределения URL для каждой операции

`operation_endpoints` заменяет весь метод URL на один `(operation, dialect, transport)` на одном провайдере. Это **не** заменяющая база URL с добавленным путем по умолчанию; параметры пути канала разрешаются этим методом:

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/operation-endpoints \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…","operation":"generate_content","dialect":"openai_chat",
       "url":"https://elsewhere.example/v1/chat/completions"}'
```

`{model}` в URL заменяется моделью провайдера, закодированной в процентах как один сегмент пути, для поверхностей, которые помещают модель в путь: `https://relay.example/v1beta/models/{model}:generateContent`.

`operation_rules` — это вторая половина: переопределение того, что канал делает для операции, для каждого провайдера. Настройки канала по умолчанию остаются в коде и не копируются в каждого нового провайдера. `POST /admin/api/providers/{id}/routing-defaults/reset` удаляет оба в одном коммите.

<a id="a-credential-row"></a>

## Строка учётных данных

| Поле | Значение |
| --- | --- |
| `label` | Необязательный. Получается из канала и учётной записи, когда вход в систему создает ее. |
| `authKind` | `api_key`, `oauth` или `cookie` — как был получен секрет. |
| `secret` | Объявленные поля канала. Никогда не возвращался; в листинге сообщается только `hasSecret`. |
| `organizationId` / `teamId` / `userId` | Владелец. Ровно один или ни одного для общих учётных данных. |
| `connectionProfileId` | Переопределяет исходящий стек провайдера. |
| `expiresAtMs` | Когда секрет подлежит обновлению. |
| `status` | `active` или `dead`. Неработающие учётные данные покидают план. |
| `version` | Защита сравнения и замены, под которой выполняется обновление. |

Секреты шифруются с помощью AES-256-GCM под мастер-ключом, а печать **привязывается к собственному идентификатору строки**, поэтому большой двоичный объект, скопированный в другую строку, не открывается. Чтение одного ответа — это отдельный проверяемый вызов:

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/credentials/{id}/reveal \
  -H "Authorization: Bearer $GPROXY_KEY"
```

Без мастер-ключа секреты хранятся **незашифрованными**. Это поддерживаемое развертывание, и двоичный файл сообщает об этом один раз при запуске.

<a id="who-can-reach-it"></a>

### Кто может достичь этого

Учётные данные аутентификации видны клиенту API, если они **не принадлежат** или когда их владелец соответствует привязке вызывающего ключа — собственному пользователю, команде или действующей организации ключа. Это привязка *ключа*, а не членство владельца, поскольку пользователь может принадлежать к двум организациям, а ключ принадлежит одной. Если бы это решало членство, каждый ключ пользователя из нескольких организаций распространялся бы на подписки каждой организации, и ни один ключ не мог бы быть уже, чем его владелец.

Видимость только сужает набор учётных данных живой аутентификации; это никогда не добавляет к этому.

<a id="acquiring-a-credential-by-logging-in"></a>

## Получение учётных данных путем входа в систему

Каналы, которые держат учётную запись, а не ключ, предлагают один или несколько из трех потоков. `GET /admin/api/channels` сообщает `loginModes` каждого канала, и запрос на тот, который канал не предлагает, отклоняется.

| Поток | Шаги | Для |
| --- | --- | --- |
| Код авторизации | начать → завершить | Перенаправление браузера с помощью PKCE |
| Код устройства | пуск → опрос, повторно | Код, введенный на другом устройстве |
| Обмен файлами cookie | обмен | Файл cookie сеанса, который уже есть у человека |

В консоли откройте вкладку учётных данных провайдера и выберите **Добавить путем входа**. Поток браузера принимает полный обратный вызов URL; опрос кода устройства происходит автоматически. Пять операций POST находятся под `/admin/api/credential-login` и привязывают ожидающий сеанс к его инициирующей пользовательской и административной области. См. [Консольное администрирование](/ru/guides/console/#credentials-and-upstream-sign-in).

GPROXY владеет всем, что не является бизнесом провайдера. **Верификатор PKCE** представляет собой 32 случайных байта, создаваемых локально и никогда не отправляемых; только его дайджест S256 достигает авторизованного URL, поэтому без него перехваченный код бесполезен. Состояние **CSRF** создается и сравнивается локально, а состояние, которое не соответствует, отклоняется *и* уничтожает сеанс, поэтому повторное воспроизведение не может быть успешным.

Ожидаемый сеанс находится в **общем кеше**, а не в этом процессе. Это то, что позволяет любому экземпляру завершить вход в систему, начатый другим — за балансировщиком нагрузки обычно находится еще один — и что делает отказ от входа в систему бесплатным: срок действия ключа истекает, а ключ с истекшим сроком действия неотличим от идентификатора, который никогда не выдавался.

**Опрос — это работа клиента API.** Опрос устройства выполняет один шаг и возвращает результат; ничего не спит и не зацикливается. Ответ содержит интервал ожидания, и провайдер `slow_down` увеличивает его для каждого последующего опроса.

Успешный вход в систему — это вставка обычных учётных данных с помощью того же примитива фиксации, который используется при записи управления. Секрет шифруется **до** создания оператора, поэтому ничто между каналом и базой данных не видит его в открытом виде, а ответом является идентификатор учётных данных и ничего больше.

<a id="refresh"></a>

### Обновить

Каналы, содержащие токены OAuth, объявляют, когда необходимо раскрыть секрет, и обновление возвращает **полную замену**, а не слияние. Хост сохраняет его с помощью сравнения и замены на `version` и публикует уведомление об изменении учётных данных.

```sh
curl -s -X POST 'http://127.0.0.1:8787/admin/api/credentials/{id}/refresh?force=true' \
  -H "Authorization: Bearer $GPROXY_KEY"
```

Провайдер, который *окончательно* отказывается от учётных данных (`invalid_grant`, отозван), помечает его как мертвый. Временный сбой транспорта или 5xx не должен: он проявляется как ошибка транспорта, поэтому хост повторяет попытку позже.

Этот путь никогда не должен терять запись. Claude меняет токен обновления при каждом обновлении, поэтому постоянство — это CAS с защитой версий, а не обновление с максимальными усилиями.

<a id="health-blocks-and-the-plan"></a>

## Здоровье, блоки и план

Разрешение полностью удаляет отключенные, устаревшие и устаревшие учётные данные. **заблокированные** учётные данные (которые имеют ограничение по скорости у провайдера) удаляются, в то время как у провайдера все еще есть разблокированные учётные данные; провайдер, чьи учётные данные *все* заблокированы, сохраняет их и размещается за каждым работоспособным провайдером. Ограничение скорости — это крайняя мера, а не отключение электроэнергии.

```sh
# what the upstream says about this credential's windows
curl -s http://127.0.0.1:8787/admin/api/credentials/{id}/quota -H "Authorization: Bearer $GPROXY_KEY"
# ask the upstream now
curl -s -X POST http://127.0.0.1:8787/admin/api/credentials/{id}/quota-probe -H "Authorization: Bearer $GPROXY_KEY"
# redeem a reset credit, where the vendor sells them
curl -s -X POST http://127.0.0.1:8787/admin/api/credentials/{id}/quota-reset -H "Authorization: Bearer $GPROXY_KEY"
# forget the recorded health
curl -s -X POST http://127.0.0.1:8787/admin/api/credentials/{id}/health-reset -H "Authorization: Bearer $GPROXY_KEY"
# the operator limits covering it
curl -s http://127.0.0.1:8787/admin/api/credentials/{id}/limits -H "Authorization: Bearer $GPROXY_KEY"
```

`POST …/status` устанавливает `active` или `dead` вручную, и на это есть причина.

<a id="connection-profiles"></a>

## Профили подключения

Профиль соединения — это исходящий стек, который принимает вызов: прокси и идентификаторы TLS и HTTP/2, которые он представляет. Сначала выбираются учётные данные, затем провайдер, затем собственный канал по умолчанию, затем экземпляр по умолчанию.

Шесть идентификаторов поставляются в виде предустановок, которые можно сохранить как `emulation` профиля:

```sh
curl -s http://127.0.0.1:8787/admin/api/tls-presets -H "Authorization: Bearer $GPROXY_KEY"
```

```text
claude / Claude CLI    codex / Codex CLI       gemini / Gemini CLI
antigravity            kiro / Kiro CLI         copilot / GitHub Copilot CLI
```

Только транспорт `wreq` представляет его. Канал, который олицетворяет CLI, возвращает свое собственное значение по умолчанию; явный профиль учётных данных, иначе провайдер все равно выиграет.

<a id="the-two-probes"></a>

## Два зонда

Это единственные вызовы руководства, которые покидают процесс.

**Connectivity** запрашивает конечную точку трассировки Cloudflare, как это развертывание выглядит снаружи, через клиентскую цепочку, называя имена областей:

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/connectivity/test \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"scope":"global"}'
```

```json
{"ok":true,"latencyMs":803,"ip":"223.166.167.192","colo":"LAX","error":null}
```

Область действия — `global`, `{"scope":"provider","provider_id":"…"}`, `{"scope":"credential","credential_id":"…"}` — тот самый транспорт, который используют его вызовы — или `{"scope":"proxy","url":"…"}` для прокси, который еще нигде не настроен. **Сбой сети - это `ok: false` с причиной, а не ошибкой**: "провайдер недоступен" - это ответ, который был запрошен.

**Тестирование и обнаружение модели** проходят через механизм точно так же, как запрос клиента API:

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/models/test \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…","model":"gpt-4o-mini"}'

curl -s -X POST http://127.0.0.1:8787/admin/api/models/discover \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…"}'
```

Они **тратят реальные учётные данные, используют реальную квоту провайдера, рассчитываются по любому бюджету, на который распространяются учётные данные, и записывают строку использования**. Пробного прогона не существует: тест, который на самом деле не обращался к провайдеру, ничего не проверял бы.

Discovery запрашивает на диалекте провайдера, поэтому имена принадлежат провайдеру. Каждый возвращается с вопросом, есть ли уже у этого провайдера строка для него и может ли включенный в комплект каталог оценить его; `POST /admin/api/models/discover/apply` вставляет те, которые вы выбираете, пропуская те, которые уже есть.

<a id="moving-a-configuration"></a>

## Перемещение конфигурации

```sh
gproxy export --out config.json --include-secrets
gproxy import --in  config.json --mode merge --source-master-key '…'
```

Что перемещается, так это конфигурация, которую *представляет** развертывание: профили подключения, провайдеры, учётные данные, каталог моделей, маршрутизация, переопределения операций, правила перезаписи, квоты, цены и строка настроек. **Идентификационные данные не передаются** — пользователи, ключи, организации, команды, разрешения и подписки принадлежат уровню продукта — как и использование или запись, поскольку их копирование привело бы к фальсификации истории, которой у места назначения никогда не было. См. [Конфигурация](/ru/reference/configuration/#moving-a-configuration) для правил мастер-ключа.

<a id="request-header-allow-lists"></a>

## Запросить списки разрешенных заголовков

Настройки → Сеть предоставляет глобальный список разрешенных заголовков запросов. Каждый провайдер может добавлять имена с помощью `config.allowed_headers`. Эффективный набор — это **объединение** глобального списка, списка провайдеров и значений каналов по умолчанию, а также `content-type`. Отсутствующие или пустые списки не добавляют записей; произвольные заголовки клиента по умолчанию удаляются. Учётные данные для проверки подлинности источника и пошаговые заголовки остаются исключенными, даже если они перечислены. Аутентификация, внедренная в канал, и настроенный статический `headers` не зависят от этой политики заголовка клиента. Изменения вступают в силу при перезагрузке конфигурации без перезаписи сохраненного списка провайдера.

<a id="glm-and-minimax"></a>

### GLM и MiniMax

`glm` использует оплату по мере использования API; `glmcode` использует план кодирования GLM. Оба принимают учётные данные `api_key` и по умолчанию используют `https://open.bigmodel.cn`. Глобальные учётные записи используют `baseUrl: "https://api.z.ai"`. `glmcode` поддерживает выделенный чат, конечные точки сообщений Claude и ответов без возврата к платному использованию API.

Оба списка моделей взяты из действующего официального каталога ZCode: запросите `/api/v1/client/configs`, загрузите возвращенный `builtin_provider_config_json`, затем выберите региональную платформу API или шаблон плана кодирования. Не существует объединенного списка моделей или резервного списка устаревших моделей. Это каталог продукции, а не подтверждение права на модель ключа.

`minimax` по умолчанию — `https://api.minimax.io`; Китайские учётные записи могут установить происхождение своей платформы API. Чат OpenAI и сообщения Claude принимают ключ подписки (план кодирования/план токена) или ключ API с оплатой по мере использования в `api_key`. Для обнаружения и детализации моделей используются официальные конечные точки `/v1/models` и `/v1/models/{id}`. Отдельные провайдеры могут маршрутизировать текст подписки и платное видео независимо друг от друга.

`glmcode` запрашивает `/api/monitor/usage/quota/limit` для получения сообщаемых процентов, независимых окон и времени сброса. Платформа `glm` пока не реализует запросы баланса счета. MiniMax соответствует официальному выбору типа ключа CLI: `/v1/token_plan/remains` или `/account/query_balance`. Эти показания в настоящее время предназначены для отображения; Ответы провайдера определяют истощение.

Видео MiniMax охватывает **H3 V2** (`MiniMax-H3`, `MiniMax-H3-Max`) и требует ключа API с оплатой по мере использования. Отправьте видеорасширение GPROXY OpenAI JSON на `/v1/videos`:

```json
{
  "model": "MiniMax-H3",
  "prompt": "A cat running through a garden",
  "duration": 5,
  "resolution": "2K",
  "aspect_ratio": "16:9"
}
```

Запросите `/v1/videos/{id}`, используя возвращенный ID, и загрузите готовый результат из `/v1/videos/{id}/content`. `frame_images` поддерживает первый/последний кадры; `input_references` поддерживает ссылки на изображения, видео и аудио. Родной MiniMax `content` тоже принимается. Sora multipart, `seconds`, `size` и устаревшие конечные точки Hailuo 2.x V1 не поддерживаются.

В списках используются `page_num`/`page_size` (`limit` сопоставляется с `page_size`); Курсоры `after`/`order` не поддерживаются. Удаление сохраняет провайдера `action`: `cancelled` отменяет поставленную в очередь задачу, а `deleted` удаляет запись задачи. Канал не осуществляет автоматический опрос и не сохраняет видеофайлы.
