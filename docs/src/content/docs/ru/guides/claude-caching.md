title: "Кэширование промптов"
description: "Настройка кэширования с помощью правил и строк magic cache, проверка использования и стоимости."
---

Оперативное кэширование обеспечивается провайдером. Попадания зависят от модели, префикса подсказки и TTL. GPROXY может добавлять маркеры с помощью правил точек кэширования или магических строк в подсказках. Маркеры не гарантируют попадание и не добавляют поддержку кэширования провайдеру, у которого ее нет.

<a id="add-a-cache-breakpoint-in-the-console"></a>

## Добавьте точку останова кеша в консоли

Добавьте правило точки кэширования на странице перезаписи провайдера. Выберите протокол провайдера и глобальную, системную цель или цель сообщения. Claude также поддерживает инструменты. Для локальной цели положительные индексы начинаются с 1, отрицательные индексы отсчитываются с конца, а пустой индекс выбирает последнюю доступную позицию.

Claude предлагает значения TTL по умолчанию, 5 минут и 1 час. Локальные точки OpenAI поддерживают TTL по умолчанию, 30 минут и 12 часов; глобальные правила — TTL по умолчанию и 30 минут. Фактическое поведение зависит от провайдера. Выберите протокол, используемый после преобразования; Gemini не поддерживается этим типом правила.

Для конфигурации API используйте `action: "cache_breakpoint"` и строку конфигурации, закодированную JSON-, в `replacement`, например:

```json
{"dialect":"claude","target":"message","index":-1,"ttl":"5m"}
```

```json
{"dialect":"openai","target":"message","index":-1,"ttl":"12h"}
```

Это правило применяется к телу запроса в настроенном порядке перезаписи. Клиенты, которые могут устанавливать поля собственного кэша, также могут напрямую использовать поля, поддерживаемые провайдером.

<a id="use-magic-strings"></a>

## Используйте волшебные струны

Клиенты без элементов управления кэшем могут включать следующие строки в текст приглашения и включать соответствующую опцию магического кэша провайдера.

<a id="the-three-strings"></a>

### Три струны

```text
GPROXY_MAGIC_STRING_TRIGGER_CACHING_CREATE_7D9ASD7A98SD7A9S8D79ASC98A7FNKJBVV80SCMSHDSIUCH
GPROXY_MAGIC_STRING_TRIGGER_CACHING_CREATE_49VA1S5V19GR4G89W2V695G9W9GV52W95V198WV5W2FC9DF
GPROXY_MAGIC_STRING_TRIGGER_CACHING_CREATE_1FAS5GV9R5H29T5Y2J9584K6O95M2NBVW52C95CX984FRJY
```

| Нить | На цели Claude | На цели OpenAI |
| --- | --- | --- |
| …`7D9ASD…` | `cache_control` со стандартным TTL API | явная точка останова |
| …`49VA1S…` | `cache_control` с `"ttl": "5m"` | `prompt_cache_breakpoint` (`"ttl": "30m"`) |
| …`1FAS5G…` | `cache_control` с `"ttl": "1h"` | `prompt_cache_breakpoint` (`"ttl": "12h"`) |

Одни и те же строки выбирают короткое и длительное хранение по целевому протоколу: Claude `5m` / `1h` соответствует OpenAI `30m` / `12h`. Строка по умолчанию не задает TTL. Локальные правила задают TTL выбранной точки, не меняя общие параметры кэширования запроса.

Поля кэша используют то же двустороннее соответствие при преобразовании Claude ↔ OpenAI Chat/Responses. Блоки системных инструкций, сообщений, изображений/документов и результатов инструментов с маркерами сохраняют свои границы. Автоматическое кэширование Claude преобразуется в явную точку в последнем блоке, если для него существует представление целевого протокола. Маркеры в определениях инструментов без эквивалента OpenAI остаются перечислены в отчете преобразования.

При преобразовании OpenAI в Claude поле верхнего уровня `cache_control` создается только при явно заданном `prompt_cache_options.mode: "implicit"`. Отсутствие объекта параметров или поля `mode`, включая пустой объект и только TTL, не включает автоматическое кэширование Claude. Явные маркеры блоков преобразуются независимо.

Они **заморожены**: они являются частью протокола клиент-прокси и не меняются между выпусками.

<a id="the-rule-that-matters-most"></a>

## Правило, которое имеет наибольшее значение

**Токен всегда удаляется независимо от того, включено ли кэширование.** Утечка маркера, находящегося в чьем-либо приглашении, никогда не требуется.

Коммутатор решает только, будет ли *точка останова* размещена там, где находился токен. При отключенном магическом кэше токены выходят и больше ничего не затрагивается: собственный `cache_control` или `prompt_cache_breakpoint` клиента остается нетронутым, а тело без токена пересылается байт за байтом, никогда не анализируется и не сериализуется повторно.

Проход голой полосы также применяется в `claudeweb`, поскольку сеанс браузера вообще не имеет управления кэшем.

<a id="enabling-it"></a>

## Включение этого

Два коммутатора `config` провайдера, по одному на семейство:

```json
{ "config": { "enable_claude_magic_cache": true,
              "enable_openai_magic_cache": true } }
```

| Выключатель | Каналы, которые это предлагают |
| --- | --- |
| `enable_claude_magic_cache` | `aws_bedrock`, `azure`, `claudeapi`, `claudecode`, `custom`, `opencodego`, `opencodezen`, `openrouter` |
| `enable_openai_magic_cache` | `aws_bedrock`, `azure`, `openai`, `codex`, `custom`, `opencodego`, `opencodezen`, `openrouter` |

Переключатель читается на **целевом диалекте**, а не на клиентском. Запрос от клиента в форме OpenAI, направляемый провайдеру Claude, сначала преобразуется в сообщения Claude, поэтому применяется переключатель Claude, а записанный маркер — `cache_control`. Клиент продолжает получать свой собственный формат.

<a id="where-a-marker-lands"></a>

## Где приземляется маркер

<a id="claude-messages"></a>

### Claude Сообщения

Сначала канонизируется тело: строковое содержимое становится массивом блоков, пустые текстовые блоки удаляются, а `cache_control`, находящийся на удаленном блоке, перемещается в ближайший кешируемый блок — именно это позволяет работать одиночному токену на отдельной строке. Мыслительные блоки сохраняются только на поворотах помощника.

Затем `system` обходится **перед** `messages`, поэтому бюджет расходуется в быстром порядке, а не в порядке ключей JSON. Каждый текстовый блок, содержащий токен, помечен:

```json
{ "cache_control": { "type": "ephemeral", "ttl": "1h" } }
```

Блок, в котором уже есть `cache_control`, остается в покое.

<a id="openai-chat-completions"></a>

### OpenAI Завершения чата

Можно пометить любое сообщение, кроме роли `function`. Обычная строка `content` разбивается на маркированную часть `text`, поскольку маркеру нужно где-то располагаться; в содержимом массива его части отмечены на своих местах.

```json
{ "type": "text", "text": "…", "prompt_cache_breakpoint": { "mode": "explicit" } }
```

<a id="openai-responses"></a>

### OpenAI Ответы

Три места по порядку:

1. **`instructions`.** Токен удаляется, а перед `input` добавляется отмеченное сообщение разработчика — `instructions` является строкой и не может содержать маркер сам по себе.
2. **`prompt.variables`**, помечено как части чата.
3. **`input`**, будь то простая строка (которая становится одним помеченным пользовательским сообщением) или массив элементов, `content` и `output` которых помечены видами `input_text`/`output_text`.

### Gemini

Никаких точек останова. Токены удаляются, и больше ничего не происходит.

<a id="the-cap-of-four"></a>

## Шапка четырех

**Не более четырех точек останова покидают прокси, включая собственную точку останова клиента.** Бюджет вычисляется путем подсчета маркеров, уже находящихся в теле, поэтому клиент, разместивший три своих собственных, оставляет место для одного.

Токены, выходящие за пределы ограничения, по-прежнему удаляются — они просто не становятся маркерами. Это то же правило, что и везде: строка никогда не достигает провайдера.

<a id="usage-and-pricing"></a>

## Использование и цены

Кэшированные токены являются отдельной метрикой, и расчетная цена их рассчитывается из строк ставок:

| Что сообщает провайдер | Метрика |
| --- | --- |
| чтение кэша | `cached_input_tokens` |
| запись в кэш по TTL | `cache_creation_tokens` + `ttl_seconds` |
| запись с неизвестным TTL | `cache_creation_tokens` |

Запись в кэш использует метрику `cache_creation_tokens`. Условие тарифа `{"ttl_seconds":43200}` выбирает цену записи на 12 часов; без этого условия действует базовая цена. Каждая группа записанных токенов тарифицируется отдельно. Чтение остается одним счетчиком `cached_input_tokens`, без TTL. Переопределения уровней: `cacheCreationPerMillion: [{"ttlSeconds":43200,"price":"5"}]`; `ttlSeconds: null` задает базовую цену. Цена указана за миллион токенов и не умножается на TTL.

Явные точки кэша OpenAI Responses и Chat поддерживают `prompt_cache_breakpoint: {"mode":"explicit","ttl":"12h"}` и `"30m"`. TTL сохраняется при преобразовании Chat ↔ Responses. Текущая [схема OpenAPI](https://github.com/openai/openai-openapi/blob/master/openapi.json) по-прежнему ограничивает `prompt_cache_options.ttl` значением `"30m"`; `prompt_cache_retention` — отдельная устаревшая настройка. Схема usage возвращает лишь сумму `cache_write_tokens`, поэтому GPROXY оставляет TTL неизвестным и не предполагает распределение между точками с разными TTL.

`cached_input_tokens` ограничен `input_tokens`: некэшированный остаток оценивается по скорости ввода, а кэшированная часть - по скорости чтения из кэша, которая ** возвращается к скорости ввода**, когда скорость чтения из кэша не существует. Записи в кэш без собственной строки скорости обнуляются. См. [Цены и уровни](/ru/reference/pricing/).

Количество токенов в записи не является обязательным — провайдер, который не сообщил о поле, не измерял ноль — в то время как каждая сумма представляет собой простое число, поскольку сумма «ничего не сообщается» действительно равна нулю.

<a id="keeping-a-hit"></a>

## Удержать хит

Правила перезаписи выполняются **после** преобразования и перед каналом, поэтому правило, редактирующее текст подсказки, может превратить ожидаемое попадание в промах. Сначала поместите стабильный контент, после него маркер и все, что касается каждого запроса, после границы — и убедитесь, что никакое правило перезаписи с широким селектором `paths` не редактирует префикс.

См. [Перезапись правил и переопределение операций](/ru/guides/rules/).
