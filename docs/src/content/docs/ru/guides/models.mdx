<VideoTutorial topic="routes" locale="ru" title="Видеоурок по моделям и маршрутам" />

Имя модели клиента редко является идентификатором модели провайдера. v4 решает эту проблему **до** запуска движка, поэтому движок видит только уже выбранную цель.

```text
request model
  → the first matching form: route name · provider/model
  → candidates, narrowed by channel, allowed providers, allowed credentials
  → ordered by (tier, health, descending weight, stable id)
  → the leading run balanced by the route's strategy
  → one (provider, credential, upstream model) per attempt
```

Используйте имя маршрута в качестве имени модели, ориентированной на клиента. Для изменения параметров запроса используйте [переписать правила](/ru/guides/rules/).

<a id="the-three-forms"></a>

## Три формы

Имя соответствует первому применимому правилу.

| Имя | решает | Попытка бюджета |
| --- | --- | --- |
| отсутствующий | каждый включенный провайдер, без модели провайдера | `settings.max_attempts` |
| **название маршрута модели** | включенные участники этого маршрута | собственный маршрут |
| `provider/model` | тот самый провайдер | `settings.max_attempts` |
| что-нибудь еще | `404 unknown_model` | — |

Названия маршрутов совпадают **точно и в первую очередь**. Руководство отклоняет имена, первый сегмент которых является именем существующего провайдера.

Префикс всегда представляет собой **имя провайдера**, а не идентификатор канала. Провайдер с именем `openai` на канале `codex` доступен как `openai/…`, точно так же, как его достигает его монтирование `/openai/v1`.

<a id="routes"></a>

## Маршруты

Маршрут — это общедоступное имя модели с провайдером/членами модели, стратегией балансировки и бюджетом попыток. Создание `main` делает `model: "main"` адресом этого маршрута.

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/routes \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"name":"main","strategy":"round_robin","maxAttempts":6}'
```

```json
{"id":"33a88261f571347c7f0408c3bd2e2164","name":"main","strategy":"round_robin",
 "maxAttempts":6,"enabled":true}
```

| Поле | Значение |
| --- | --- |
| `name` | Глобально уникальный. Клиенты отправляют это точное имя как `model`. |
| `sessionAffinity` | Повторно используйте успешный целевой провайдер/модель для сеанса; по умолчанию выключено. Выбор учётных данных остается обязанностью провайдера. |
| `strategy` | `round_robin`, `weighted` или `failover`. |
| `maxAttempts` | Общий бюджет попытки, включая первый звонок. `settings.maxAttempts` (по умолчанию 6) — это жесткий потолок во время выполнения. |

<a id="members"></a>

## Члены

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/route-members \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"routeId":"…","providerId":"…","upstreamModel":"gpt-4o-mini",
       "tier":0,"weight":100}'
```

| Поле | Значение |
| --- | --- |
| `providerId`, `upstreamModel` | Куда этот участник отправляет трафик. Имя модели — это явная строка, а не внешний ключ каталога. |
| `tier` | Более низкий является предпочтительным. Уровень 0 исчерпывается до того, как уровень 1 увидит какой-либо трафик. |
| `weight` | Положительный, по умолчанию 100. Разделяет трафик внутри уровня и упорядочивает кандидатов на аварийное переключение. |
| `enabled` | Участник с ограниченными возможностями покидает план. |

Участник не называет учётные данные. Какие учётные данные внутри выбранного провайдера обслуживают вызов, это отдельное решение, которое принимает механизм, и он переключается между учётными данными этого провайдера, прежде чем план перейдет к следующему участнику.

<a id="how-the-order-is-decided"></a>

### Как определяется порядок

Кандидаты сортируются по `(tier, health, descending weight, stable id)`.

**Уровень – это жесткое предпочтение.** Балансируется только лидирующая серия — кандидаты, разделяющие уровень *и* здоровья первого, и то по стратегии:

| Стратегия | Влияние на лидерство |
| --- | --- |
| `round_robin` | вращает его по счетчику маршрутов |
| `weighted` | продвигает гладкий утяжеленный медиатор вперед |
| `failover` | оставляет это в покое: отсортированный порядок *является* ответом |

Вращение — это счетчик, а не случайный розыгрыш, поэтому Wasm и Native ведут себя одинаково, и последовательность воспроизводима.

Отключенные, устаревшие и устаревшие учётные данные удаляются полностью. Заблокированные учётные данные удаляются, в то время как у их провайдера все еще есть разблокированные учётные данные; провайдер, чьи учётные данные **все** заблокированы, хранит их и сортирует по каждому работоспособному провайдеру. Ограничение скорости — это крайняя мера, а не отключение электроэнергии.

Имя, которое было разрешено, но ничего не достигло, — это ошибка, отличная от имени, которое никогда не было известно — проблема конфигурации, а не неизвестная модель.

<a id="route-names"></a>

## Названия маршрутов

Создавайте и редактируйте названия прямо на маршрутах; отдельного сопоставления общедоступных имен не требуется.

<a id="namespaces"></a>

### Пространства имен

Имя с `/` создает пространство имен во время выполнения: создание маршрута `acme/fast` делает `acme` монтируемым, а `/acme/v1/chat/completions` с `{"model":"fast"}` разрешает `acme/fast`.

```sh
curl -s http://127.0.0.1:8787/acme/v1/chat/completions \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"model":"fast","messages":[{"role":"user","content":"hi"}]}'
```

Пространство имен — это **индекс имени**, а не хранимая группа и не область владения. Ничто не создано и ничто не принадлежит ему.

<a id="reserved-first-segments"></a>

### Зарезервированные первые сегменты

Имя маршрута, первый сегмент которого является именем существующего провайдера, отклоняется, чтобы избежать неоднозначной маршрутизации пространства имен/префикса:

```json
{"error":{"code":"invalid_request","message":"invalid request: `codex/` is reserved:
 a first segment naming a provider already means `provider/model` narrowing;
 choose a distinct model route name"}}
```

Все остальное в порядке. `coding/fast` — вполне хорошее публичное имя.

<a id="the-model-catalogue"></a>

## Каталог моделей

Две таблицы, и ни одна из них не требуется для маршрутизации.

**`provider_models`** записывает, какие имена провайдеров обслуживает провайдер:

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/provider-models \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…","upstreamName":"gpt-4o-mini"}'
```

```json
{"id":"f32df0bb6378c03e70f7c3aa6315a3b8","providerId":"5a45fd807be0…",
 "upstreamName":"gpt-4o-mini","modelId":null,"metadata":{},"enabled":true}
```

Здесь пишет открытие. **`models`** — это глобальный каталог, на который может указывать строка `provider_models`: одно имя, его метаданные и словарь токенизатора, который должен использовать для него оценка токена.

Маршрутизация может соответствовать именам, отсутствующим в обоих случаях. Участник маршрута называет свою модель провайдера простой строкой, поэтому строка каталога является документацией и ценовым материалом, а не обязательным условием.

<a id="filling-it-from-the-upstream"></a>

### Заполнение от провайдера

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/models/discover \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…"}'
```

Discovery запрашивает на **собственном диалекте** провайдера, поэтому ничего не преобразуется, а имена принадлежат провайдеру. В каждом ответе указывается, есть ли уже у этого провайдера строка для него и может ли прилагаемый каталог оценить его. `POST /admin/api/models/discover/apply` вставляет те, которые вы называете, пропуская те, которые уже есть, поэтому применение обнаружения дважды — то же самое, что и один раз.

И этот, и `POST /admin/api/models/test` используют настоящие учётные данные и записывают реальную строку использования. См. [два зонда](/ru/guides/providers/#the-two-probes).

Связанный каталог — имена, контекстные окна и цены по умолчанию, о которых известно в этом выпуске — представляет собой снимок, сделанный при создании актива, а не действующий каталог:

```sh
curl -s http://127.0.0.1:8787/admin/api/default-model-catalog -H "Authorization: Bearer $GPROXY_KEY"
curl -s -X POST http://127.0.0.1:8787/admin/api/default-model-catalog/apply-prices \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…","modelIds":["gpt-4o-mini"],"overwrite":false}'
```

`overwrite: false` — это то, что делает повторное применение безопасным: правило, отредактированное оператором, сохраняет свое редактирование и сообщается как пропущенное.

<a id="what-a-caller-sees"></a>

## Что видит клиент API

`GET /v1/models` возвращает настроенный каталог: имена маршрутов и `provider/model`, отфильтрованные по именам, которые может использовать клиент API. Он не перемещается между каталогами провайдеров. Добавьте или импортируйте модели провайдеров, чтобы опубликовать их здесь. Префикс — это настроенное имя маршрута провайдера.

Эти две формы эквивалентны: базовый URL `/provider-A/v1` с моделью `gpt-5` или базовый URL `/v1` с моделью `provider-A/gpt-5`. `GET /provider-A/v1/models` запрашивает только провайдера A и сохраняет исходные названия моделей.

Портал также включает имена, которые клиент API не может использовать, помеченные `permitted`:

```sh
curl -s http://127.0.0.1:8787/portal/api/models -H "Authorization: Bearer $GPROXY_KEY"
```

```json
[{"name":"provider-A/gpt-4o-mini","providerCount":1,"channelIds":["custom"],"permitted":true},
 {"name":"fast","providerCount":1,"channelIds":["custom"],"permitted":true}]
```

Имя, которого не достигают правила клиента API, остается в списке с `permitted: false`. v3 удалил такие строки; v4 этого не делает, потому что список, который молчаливо опускает, делает «эту модель 404s» и «вам не разрешена эта модель» одним и тем же наблюдением — и защищать нечего, поскольку открытое имя — это конфигурация экземпляра, которую оператор все равно публикует.

Что *скрывается*, так это идентификаторы провайдера, стоящие за именем: в ответе сообщается количество и канал, которые говорят, насколько избыточно имя без названия оборудования. `provider/model` использует отображаемое имя провайдера; переименование провайдера приводит к изменению префикса его модели и базы URL.

<a id="global-models-and-default-metadata"></a>

### Глобальные модели и метаданные по умолчанию

В разделе **Модели** (`/console/model-catalog`) консоли перечислены модели, сохраненные в базе данных, с использованием той же конечной точки `/admin/api/models` в качестве селекторов разрешений. Пустая база данных возвращает пустой список. **Загрузить модели по умолчанию** импортирует выбранные записи из таблицы связанных моделей и сохраняет существующие модели без изменений; загрузка метаданных модели не меняет правила ценообразования. Модели также можно добавлять вручную. Удаление модели удаляет ее из списка; он не восстанавливается из связанных данных во время чтения. На странице показаны сохраненные возможности и ограничения, ассоциации провайдеров и справочные цены, если они доступны.

Идентификаторы объединенных моделей представляют собой неполные имена, например `claude-sonnet-4`, а не `anthropic/claude-sonnet-4`. Исходные URL-адреса и необработанные цены сохраняют свое происхождение. Полноценные имена провайдеров по-прежнему разрешаются по базовому имени. При сопоставлении цен по умолчанию предпочтение отдается самому длинному фрагменту модели соответствия; импорт цен провайдера сохраняет фактическое имя провайдера в качестве шаблона правила. Цены редактируются в существующих диалоговых окнах глобальной модели и модели провайдера.

Discovery сначала соответствует полной ID модели, а затем уникальному базовому имени; неоднозначные имена не получают значений по умолчанию. Порядок слияния объединяет значения по умолчанию → поля провайдера, отличные от null → локальные переопределения. Импорт консоли заполняет только недостающие поля в существующих моделях провайдеров. Метаданные копируются во время импорта; изменения в каталоге не приводят к автоматическому изменению ранее импортированных строк провайдера.

Цены по умолчанию представляют собой снимок OpenRouter, а не контракт каждого провайдера. Применение цен по умолчанию создает глобальные правила ценообразования без замены существующего правила тем же шаблоном. Редактор цен управляет тарифами, уровнями контекста и уровнями обслуживания. Правила, специфичные для провайдера, имеют приоритет над глобальными правилами.

Обновите связанный ресурс с помощью `node scripts/update-openrouter-model-catalog.mjs` или используйте `--input response.json` для автономного обновления. Конечная точка общедоступной модели не нуждается в ключе; дополнительные учётные данные доступны только для чтения из `OPENROUTER_API_KEY`. Генератор сохраняет необработанные данные `source_pricing` для просмотра и сопоставляет только поддерживаемые единицы выставления счетов. После преобразования единиц измерения цены округляются до девяти десятичных знаков с использованием ближайшего округления с привязкой к четному; импорт цен по умолчанию использует то же правило. Отсутствующие или динамические цены не означают бесплатность. Прежде чем добавлять товары с официальных страниц цен, проверьте точную версию модели, регион, единицу измерения и пороговое значение, а не угадывайте недостающую цену.
