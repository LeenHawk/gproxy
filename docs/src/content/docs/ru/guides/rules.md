Добавляйте правила со страницы перезаписи провайдера, выбирая тип и вводя его настройки. Новые провайдеры получают связанный набор правил по умолчанию с тем же именем. Используйте расширенные привязки, когда нескольким провайдерам необходимо использовать общие правила.

<a id="rule-types"></a>

## Типы правил

| Тип консоли | Цель | API `action` |
| --- | --- | --- |
| Системный текст | Добавление или добавление текста к системным инструкциям | `system_text` |
| Точка останова кэша | Добавляйте глобальные, системные, сообщения или маркеры кэша инструментов, специфичные для протокола. | `cache_breakpoint` |
| JSON переписать | Установите или удалите поле или объедините объект | `set`, `delete`, `merge` |
| Преобразование текста | Применение регулярного выражения к основному тексту, заголовкам или значениям запроса. | `replace` |
| Заголовок | Установите значение или объедините значения, разделенные запятыми. | `header_set`, `header_merge` |

Системный текст поддерживает Claude, OpenAI Chat, ответы (включая WebSocket) и Gemini. Точки останова кэша поддерживают форматы Claude и OpenAI; информацию о позициях и TTL см. в [Оперативное кэширование](/ru/guides/claude-caching/).

<a id="advanced-json-editing"></a>

## Расширенное редактирование JSON

При создании или редактировании правила в наборе правил выберите **Дополнительно JSON**, чтобы вставить один объект правила версии 4. Это также доступно на странице перезаписи провайдера. Переключитесь между формой и JSON или отформатируйте JSON. Неверный ввод остается в редакторе с ошибкой; сохранение также проверяет возможность выполнения правила.

Например, замените `"type":"function"}` в теле на `"type":"function","strict":false}`:

```json
{
  "action": "replace",
  "phase": "request",
  "target": "body",
  "pattern": "\"type\":\"function\"\\}",
  "replacement": "\"type\":\"function\",\"strict\":false}"
}
```

Используйте поля v4 `action`, `pattern` и `replacement`. Страница управляет набором правил ID и порядком, поэтому опустите их из JSON. Могут быть включены дополнительные фильтры и `enabled`. Пропущенные фильтры не накладывают никаких ограничений, а для `enabled` по умолчанию используется true. Каждое редактирование принимает один объект правила, а не массив.

<a id="execution-order"></a>

## Порядок выполнения

Запросы преобразуются в протокол провайдера, перезаписываются и затем отправляются по каналу. Ответы перезаписываются перед преобразованием обратно в клиентский протокол. Поэтому пути правил должны использовать **формат провайдера**.

Например, запрос чата OpenAI, направленный на Claude, использует поля `system` и `messages` Claude по времени выполнения правил запроса.

Включены привязки наборов правил, и правила в каждом наборе выполняются в порядке `sortOrder`, а затем ID. Каждое правило видит выходные данные предыдущего правила. Правила системного текста и точек кэширования следуют в том же порядке.

<a id="fields-and-regular-expressions"></a>

## Поля и регулярные выражения

Для редактирования JSON требуются такие пути, как `temperature` или `messages.*.content`. Сегмент `*` выбирает все элементы. Для `set` требуется допустимое значение JSON, для `merge` требуется объект JSON, а для `delete` значение не требуется.

Преобразования текста используют регулярные выражения Rust, включая замены `(?i)`, `(?s)`, `$1` и `${name}`. Пути к телу заменяют выбранные строковые значения JSON. Без путей они работают с полным текстом тела; позаботьтесь о сохранении действующего JSON.

Для правил заголовка и запроса требуется `targetName`. `header_set` заменяет значение заголовка. `header_merge` объединяет значения, разделенные запятыми, и удаляет дубликаты. Избегайте хранения секретов провайдера в общих правилах.

<a id="filters"></a>

## Фильтры

| Фильтр | Матчи |
| --- | --- |
| Операция и протокол | Преобразованная операция, выполненная на провайдере |
| Модель | Название провайдера или запрошенной модели с подстановочными знаками `*` и `?` |
| Заголовки запросов | Регулярное выражение для входящих заголовков |
| Трансляция события | Имя события SSE или JSON `type` для правил тела |

Все поставляемые фильтры должны соответствовать друг другу. Пропущенные фильтры не накладывают ограничений. Определите область действия правил совместимости, специфичных для клиента, по заголовкам запросов, чтобы они не влияли на других клиентов.

Предложения моделей содержат только сохраненные модели и варианты провайдеров. На странице провайдера перечислены модели этого провайдера; отдельная страница набора правил объединяет модели от подключенных провайдеров. Для неприсоединенного набора предложений нет, но вы все равно можете ввести название модели или шаблон, например `gpt-*`. Предложения не извлекают каталоги моделей провайдеров.

<a id="streaming-responses"></a>

## Потоковая передача ответов

Перезапись тела выполняется для полных событий, таких как событие SSE или элемент массива JSON, а не для сетевых фрагментов. Событие, превышающее `settings.maxStreamEventBytes`, завершается неудачно. Используйте фильтр событий для таргетинга на определенные типы событий.

<a id="management-api"></a>

## Управление API

В этом примере `widget` заменяется на `gadget` в выбранных строках. Замените фактический набор правил ID.

```sh
curl -sS -X POST http://127.0.0.1:8787/admin/api/rules \
  -H "Authorization: Bearer $GPROXY_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"ruleSetId":"your-rule-set-id","action":"replace",
       "phase":"request","target":"body","paths":["messages.*.content"],
       "pattern":"(?i)\\bwidget\\b","replacement":"gadget",
       "filterOperationKeys":[{"operation":"generate_content","dialect":"openai_chat"}]}'
```

`PUT /admin/api/rule-sets/{id}/rules` заменяет полный список правил. Для системного текста и точек останова в кэше `replacement` содержит строку конфигурации в кодировке JSON-encoded. Консоль создаст его за вас.

<a id="compatibility-presets"></a>

## Пресеты совместимости

`GET /admin/api/rule-presets` возвращает встроенный OpenCode, предустановки агента-моно, Aider, Cline, Continue и Cursor. Запросите конечную точку для текущих правил.

`POST /admin/api/rule-sets/{id}/rule-presets/{preset}` **заменяет** существующие правила набора. Чтобы сохранить существующие правила, сначала экспортируйте или прочитайте их и сохраните объединенный список.

<a id="protocol-and-endpoint-overrides"></a>

## Переопределение протокола и конечной точки

Правила маршрутизации провайдера выбирают протокол провайдера. Маршруты моделей выбирают провайдеров; это отдельные настройки.

- `operation_rules` переопределяет список протоколов провайдера для операции. Проходит поддерживаемый клиентский протокол; в противном случае преобразование нацелено на первый протокол в списке.
- `operation_endpoints` переопределяет полную конечную точку URL для операции, протокола и транспорта.

Например, измените протоколы генерации:

```sh
curl -sS -X POST http://127.0.0.1:8787/admin/api/operation-rules \
  -H "Authorization: Bearer $GPROXY_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"providerId":"your-provider-id","operation":"generate_content",
       "action":"dialects","target":["claude","openai_chat"]}'
```

Без переопределений применяются значения канала по умолчанию. `POST /admin/api/providers/{id}/routing-defaults/reset` очищает операцию провайдера и переопределения конечной точки.

Канал `custom` также требует конфигурации `dialects`, например `["openai_chat", "openai"]`. В случае сбоя операции проверьте поддержку провайдера, этот список и переопределения операций.

<a id="body-and-header-conditions"></a>

## Условия тела и заголовка

Добавьте `filterBody` и/или `filterHeader`, чтобы активировать существующее действие. Оба условия и все остальные настроенные фильтры должны совпадать.

```json
{
  "action": "set",
  "phase": "request",
  "target": "body",
  "paths": [
    "service_tier"
  ],
  "pattern": "",
  "replacement": "\"priority\"",
  "filterBody": {
    "path": "reasoning.effort",
    "op": "eq",
    "value": "high"
  },
  "filterHeader": {
    "name": "x-client-mode",
    "op": "eq",
    "value": "fast"
  }
}
```

`filterBody` считывает текущую полезную нагрузку JSON после предыдущих правил. Он поддерживается только для целей тела. Пути принимают ключи, разделенные точкой, и индексы массивов без подстановочных знаков. Равенство сохраняет типы JSON; отсутствует, отличается от `null`. Неверный JSON никогда не соответствует состоянию тела, включая `not_exists`.

`filterHeader` считывает исходные заголовки входящих запросов для любой цели и фазы. Имена заголовков не чувствительны к регистру; значения представляют собой точные строки с учетом регистра без разделения запятыми. При повторяющихся заголовках `eq` соответствует любому равному значению; `ne` требует присутствия заголовка без равного значения.

Операторы: `eq`, `ne`, `exists` и `not_exists`. Для равенства/неравенства требуется `value`; операторы существования отвергают это. Отсутствующее поле не удовлетворяет требованиям `ne`. Условия выполняются для всего тела, события SSE, записи NDJSON, элемента JSON-array или сообщения WebSocket без состояния перекрестного сообщения. Очистите состояние с помощью `null`; Пропущенные поля PATCH сохраняют существующие условия.

<a id="jmespath-expressions"></a>

### Выражения JMESPath

`filterBody` также принимает строку выражения JMESPath. Он оценивает текущее тело, и действие выполняет только логическое значение `true`. Ошибки типа, неизвестные функции, другие ошибки вычислений и нелогические результаты не совпадают. Синтаксис проверяется при сохранении. Существующая форма объекта `{ "path", "op", "value" }` остается поддерживаемой.

Это правило устанавливает для `max_tokens` значение 0 только в том случае, если текстовый блок в последнем сообщении содержит маркер активности. Более ранние сообщения не могут его вызвать:

```json
{
  "action": "set",
  "phase": "request",
  "target": "body",
  "paths": [
    "max_tokens"
  ],
  "replacement": "0",
  "filterBody": "length(messages[-1].content[?type(text) == 'string' && contains(text, '[cache-keepalive]')]) > `0`"
}
```

Отрицательные индексы, прогнозы, `contains()`, сравнения и логическая композиция следуют за [Спецификация JMESPath](https://jmespath.org/specification.html). Отсутствующие поля оцениваются как `null` и могут быть явно проверены; Полезные нагрузки, отличные от JSON, никогда не совпадают. `paths` действия по-прежнему использует существующий синтаксис точечного пути независимо от выражения.

Выражения компилируются один раз. Неизмененные полезные данные используют один преобразованный документ JMESPath; фактическое предыдущее редактирование тела делает этот снимок недействительным. Правила без выражений не создают этого дополнительного представления. Каждая единица потока независима. Запросы, проходящие через весь документ, по-прежнему масштабируются вместе с его размером.
