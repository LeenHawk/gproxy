Канал знает одно семейство провайдеров: его URL-адреса, способ введения учётных данных, на каких диалектах сети он говорит, как его поток сообщает об использовании и — для провайдеров в стиле учётной записи — как войти в систему, обновить и прочитать квоту.

Все остальное — чужая работа. Маршрутизация, выбор учётных данных, аварийное переключение, преобразование протокола, расчет и захват относятся к механизму, и **ничто в канале не читает базу данных и не выбирает транспорт**.

Канал компилируется, никогда не загружается во время выполнения, и он может находиться в двух местах:

- **В этом репозитории**: модуль `gproxy-channel` с собственной функцией Cargo, добавленный по запросу. Он достигает каждого хоста, включая Workers. Это [девять шагов](#the-nine-steps).
- **В вашем собственном ящике**: тип, реализующий `BaseChannel` в соответствии с общедоступным контрактом, и собственный двоичный файл или Worker, который является стандартным, плюс этот тип. В этом репозитории ничего не меняется. Это [за пределами этого репозитория](#outside-this-repository).

Оба реализуют одну и ту же черту одинаково; отличается только регистрация. По умолчанию конкретный канал не компилируется.

<a id="does-it-need-one"></a>

## Нужен ли он?

Канал — это код, который необходимо поддерживать против протокола провайдера. Провайдер получает один только в том случае, если в строке провайдера не может быть указано, что ему нужно: путь, который перемещается вместе с операцией, тело, которое необходимо переписать, поверхность учётной записи для чтения, идентификатор клиента, который необходимо представить.

Провайдер, вся разница которого состоит в источнике и заголовке, является провайдером `custom`. См. [провайдеры, которым не нужен канал](/ru/guides/providers/#vendors-that-need-no-channel).

<a id="the-contract"></a>

## Контракт

`BaseChannel` — единственная необходимая черта, а `id` — единственный обязательный метод. Каждая операция протокола имеет свой собственный асинхронный метод с реализацией **по умолчанию**: создайте запрос с помощью `prepare` (HTTP) или `prepare_connect` (WebSocket), а затем передайте его назначенному клиенту.

Оба хука подготовки по умолчанию имеют значение «не поддерживается», поэтому канал поддерживает именно то, что он подготавливает или переопределяет, **никогда больше**.

```text
the host selects provider, credential, client
  → ChannelBinding::new(&channel, provider, credential, client)
  → binding.send(OperationKey, WireRequest<HttpBody>)
    binding.connect(OperationKey, WireRequest<()>)
  → the named operation method on BaseChannel
  → default: prepare + client.send  /  prepare_connect + client.connect
    or the channel's own multi-call flow through the same client
```

То, что передает хост, является заимствованным и общедоступным, где это может быть:

| Тип | держит |
| --- | --- |
| `ProviderView` | `id`, `channel`, дополнительный `base_url` и JSON `config` канал декодирует в свои собственные типизированные настройки |
| `CredentialView` | `id`, `provider_id`, `auth_kind`, JSON `secret` (нет `Debug`, нет `Serialize`), публичный `metadata`, записанный хостом, `version`, `expires_at_ms` |
| `OperationContext` | оба представления, диалект операции, `WireRequest`, собственный клиент, состояние перекрестного запроса, идентификатор экземпляра хоста и необязательное переопределение конечной точки |
| `CredentialContext` | провайдер, учётные данные и клиент для обновления, квот и услуг |

<a id="rules-every-channel-follows"></a>

### Правила, которым следует каждый канал

- **Подготовка является синхронной и чистой**: без ввода-вывода, без скрытого состояния, без создания клиента. Переопределение операции может совершить несколько обменов, но только через `context.client`, и может оставить его до завершения работы после завершения потока ответов.
- **Аутентификация источника никогда не достигает провайдера.** Помощник пересылки отбрасывает поэтапные заголовки, а также `host`, `content-length`, `authorization`, `x-api-key`, `x-goog-api-key` и `api-key`; канал добавляет свою собственную аутентификацию из учётных данных. Разрешенные заголовки клиента представляют собой объединение глобального списка разрешений, провайдера `allowed_headers` и объявленных заголовков канала; `content-type` всегда пасует. Отсутствующие или пустые списки не добавляют записей.
- **Переопределение конечной точки — это полный метод URL**, заменяющий базовый URL и путь канала по умолчанию, а не базу для добавления.
- **Отсутствие 2xx — это ответ, а не ошибка.** Статус, заголовки и ленивое тело возвращаются в исходном виде. Вариант ошибки предназначен для вызовов *возможностей* (вход в систему, обновление, квота) и для промежуточного обмена внутри переопределения нескольких вызовов, где неверный ответ не является возвращаемым ответом.
- **`RefreshRejected` означает, что провайдер окончательно отказался от учётных данных** (`invalid_grant`, отозван), и хост помечает их как недействительные. Временный сбой транспорта или 5xx должен отображаться как ошибка транспорта, поэтому хост повторит попытку позже. Ошибка убивает рабочий аккаунт.
- **`ContinuationElsewhere`** сообщает, что активное соединение с провайдером поддерживается другим хост-процессом. Хост перенаправляет; с учётными данными все в порядке.

<a id="the-optional-abilities"></a>

## Необязательные возможности

Каждый из них представляет собой независимую черту, лежащую в основе аксессора по умолчанию `None`. Канал реализует те, которые есть у его провайдера, и ничто их не связывает — канал может сообщать об окнах квот, не предлагая сброса.

| Аксессор | Цель |
| --- | --- |
| `credential_refresh` | Создайте **полную замену** секрета и срок его действия истечет; хост сохраняет его при сравнении и обмене на `version` |
| `oauth_authorization_code` | Создайте авторизацию URL для запроса и состояния PKCE, предоставляемого хостом; обменять код |
| `oauth_device_code` | `start` и один шаг `poll`. Планирование принадлежит хосту |
| `cookie_login` | Обменять вставленный файл cookie на учётные данные и его общедоступные метаданные |
| `quota_model` | Синхронный и чистый: какие размеры квоты имеет учётные данные, исходя из его `auth_kind` и метаданных |
| `quota_query` | Чтение снимка квоты из конечной точки использования провайдера |
| `quota_headers` | Превратите заголовки ответов в записи квот; пусто означает, что ничего не сообщается |
| `quota_reset` | Кредиты и ручной сброс у провайдеров, которые их продают |
| `usage_extras` | Собственные поля использования провайдера, читаемые рядом со стандартным использованием, которое хост уже взял из сформированного ответа |
| `response_reason_observer` | Классифицируйте необработанный ответ провайдера (ограничение скорости, перегрузка, отказ…). По умолчанию анализируются стандартные JSON и SSE; переопределить только для формата частной телеграфной связи |
| `websocket_response_reason` | То же самое для одного полного входящего сообщения WebSocket |
| `services` | Маршруты плоскости управления провайдера — см. [CLI Клиенты](/ru/guides/cli-clients/) |

Само использование не требует никаких способностей: хост считывает его из стандартного ответа, который формирует канал, а канал, который ничего не сообщает, является **несообщаемым**, а не нулевым.

Две возможности дескриптора не могут быть получены из средства доступа, поэтому канал, в котором они есть, говорит об этом в своем собственном `descriptor`: `websocket` (он переопределяет операцию сокета) и `paid_usage` (его `QuotaModel::allows_paid_usage` считывает флаг метаданных учётных данных `allow_paid_usage`, что заставляет консоль предлагать этот переключатель).

Память перекрестных запросов ограничивается хостом одним провайдером и одним учётным данными аутентификации и записывается в режиме сравнения и замены. Привязка по умолчанию запрещает каждую запись, поэтому каналу, которому нужно состояние, необходимо предоставить его.

<a id="the-login-pocket"></a>

### Состояние процесса входа

Оба потока OAuth содержат карман для фактов, необходимых каналу, на дальней стороне авторизации человека: то, что вставляет `start`, возвращается вместе с авторизацией. Форма у него собственная — нестандартный дескриптор устройства, клиент, логин, прописанный под себя.

**Этот карман может хранить секреты**, в отличие от общедоступного `provider_fields`, который хост публикует в качестве метаданных учётных данных: он живет в сеансе входа в систему хоста, который недолговечен, хранится в кеше и никогда не отображается, и он исчезает, когда вход в систему заканчивается. Все, что должно пережить вход в систему, возвращается из обмена — общедоступные факты в виде метаданных, секретные — в виде секретов провайдера, которые шифруются токенами и никогда не становятся метаданными.

<a id="the-nine-steps"></a>

## Девять шагов

Используйте `custom` (ключ API) и `codex` (учётная запись OAuth) в качестве двух ссылок.

1. **Объявите эту функцию** в `crates/gproxy-channel/Cargo.toml`, перечислив только необязательные зависимости, необходимые каналу. Зависимость только для Wasm находится в целевой таблице `cfg(target_arch = "wasm32")`.

   ```toml
   [features]
   # One-line description of the upstream and what the channel covers.
   acme = ["dep:base64", "dep:web-time"]
   ```

2. **Добавьте одну строку** в список `channels!` в `src/channels/mod.rs`: функцию, модуль и значение, регистрируемое хостом. Эта единственная строка объявляет модуль и помещает канал в `compiled_in()`, и именно так его находит каждый хост.

   ```rust
   "acme" => acme, acme::Acme;
   ```

   Если канал использует `shared`, расширьте также собственный `cfg(any(...))` этого модуля.

3. **Размещайте модуль по одному элементу в файле.** Небольшой канал — это один `acme.rs`; больший каталог:

   ```text
   src/channels/acme/
     mod.rs        the id, the unit struct, re-exports, the module doc
     config.rs     the provider `config` JSON, serde(default), unknown keys ignored
     request.rs    prepare / prepare_connect / overridden operations
     oauth.rs      the login and refresh abilities
     quota.rs      the quota abilities
     usage.rs      the usage abilities
     services.rs   the vendor control-plane routes
   ```

   **В документации модуля указан источник каждого факта о проводе** — ссылка провайдера на API или источник CLI под `samples/`. Правда телепередачи никогда не является кодом другого канала.

4. **Реализуйте `BaseChannel`.** Минимум: `id`, `native_dialects` и `prepare`. Структура представляет собой единицу без сохранения состояния, поэтому один экземпляр обслуживает каждого провайдера этого канала.

   Также переопределите `descriptor`. По умолчанию считываются средства доступа к возможностям, и только канал знает свое отображаемое имя и ключи, которые он декодирует из провайдера `config` JSON. **Этот дескриптор — это все, что нужно для управления UI для отображения формы провайдера** — в рамках функции `ts` это также тип TypeScript — поэтому ключ, не включенный в него, является ключом, который никто не может установить.

   Переопределите метод операции вместо `prepare`, когда провайдеру требуется более одного обмена, локально синтезированный ответ, другой транспорт или ответ, переписанный на объявленный собственный диалект.

5. **Объявите, что отправляет клиент провайдера.** Если канал олицетворяет CLI, экспортируйте его константу заголовка и создайте на ее основе список разрешений, чтобы `allowed_headers` провайдера не мог удалить собственные заголовки CLI. Передайте эти заголовки идентификаторов в раскрывающийся список помощника по пересылке, чтобы **клиент не мог их подделать**. Возвращает соединение по умолчанию, когда провайдер снимает отпечатки пальцев своих клиентов; явный профиль учётных данных или провайдера аутентификации по-прежнему имеет преимущество.

6. **Добавляйте способности как отдельные типы** и возвращайте их из средств доступа. Соблюдайте правила каждого типажа: обновление возвращает полную замену, а не слияние; Измерения квот считывают факты плана из метаданных учётных данных, а не из сети; наблюдатель использования создает кумулятивные снимки, и его `finish` получает полные или прерванные данные **от хоста**, поскольку EOF сам по себе не устанавливает полное использование.

7. **Включите в `src/channels/shared/` механизмы многоразового использования** с учетом функций, которые их используют. Политика остается в русле; общий модуль выполняет только то, что запрашивает канал.

8. **Проверьте код** в `tests/<id>.rs` за `#![cfg(feature = "…")]`. Создайте представления учётных данных провайдера и аутентификации вручную, вызовите `prepare` с секретным ключом и подтвердите URL, введенную аутентификацию и отброшенные заголовки. Передать захваченные кадры наблюдателю использования; анализировать записанные заголовки квот и тела использования. Исходящий клиент со сценарием выполняет переопределение нескольких вызовов. **Не проверяйте двигатель отсюда.**

9. **Пересылайте функцию на каждый хост.** Механизм никогда сам не перечисляет каналы: `gproxy-sdk` регистрирует все, что возвращает `compiled_in()`, поэтому канал становится доступным из двоичного файла именно тогда, когда набор функций этого двоичного файла достигает своей функции. Добавьте функцию с тем же именем в:

   | Файл | Строка для добавления |
   | --- | --- |
   | `crates/gproxy-sdk/Cargo.toml` | `acme = ["gproxy-channel/acme"]` и `"acme"` в списке `channels` |
   | `crates/gproxy/Cargo.toml` | `acme = ["gproxy-sdk/acme"]` |
   | `crates/gproxy-host-edge/Cargo.toml` | `acme = ["gproxy-sdk/acme"]` |
   | `crates/gproxy-app/src/v3/channels.rs` | идентификатор в `V4_CHANNELS`, поэтому импорт v3 принимает его |

   Дубликат идентификатора отклоняется, а провайдер, называющий незарегистрированный канал, является ошибкой конфигурации, а не резервным вариантом.

<a id="finish"></a>

## Завершение

```sh
cargo fmt --all
cargo clippy -p gproxy-channel --all-features --all-targets -- -D warnings
cargo clippy -p gproxy-channel --all-features --target wasm32-unknown-unknown --lib -- -D warnings
cargo test   -p gproxy-channel --all-features
```

**Каждый канал создается для собственных целей и для `wasm32-unknown-unknown`**, что не позволяет хосту Workers быть сокращенным набором каналов. Обнаружение ворса приводит к изменению кода, а не к `#[allow]`.

Как только он введен, больше ничего не требуется: провайдер на новом канале появляется в `GET /admin/api/channels` со своим дескриптором, а управляющий UI отображает свою форму на его основе.

<a id="outside-this-repository"></a>

## За пределами этого репозитория

Канал может жить в собственном ящике и поставляться без форка на любом хосте: в собственном двоичном файле, который представляет собой стандартный `gproxy` — те же команды, флаги, консоль и база данных — или Worker, который является стандартным GPROXY Worker, каждый из которых имеет канал, зарегистрированный рядом со встроенными. `examples/channel-plugin` — это полный рабочий набор всех трех ящиков: OpenAI-совместимый канал API-key в одном файле и точка входа в несколько строк для каждого хоста.

<a id="the-layout"></a>

### Структура проекта

```text
my-gproxy/
  channel/    the channel: a unit struct implementing BaseChannel, no host
  native/     the gproxy binary, carrying it
  edge/       the Cloudflare Worker, carrying it (only if you deploy there)
```

Канал представляет собой отдельный контейнер, поэтому от него могут зависеть оба хоста. Собственный хост не может быть одной из его зависимостей: `gproxy` не собирает для Wasm, и Worker тоже не будет собирать.

```rust
// native/src/main.rs
use std::{process::ExitCode, sync::Arc};

fn main() -> ExitCode {
    gproxy::main_with(vec![Arc::new(my_channel::Acme)])
}
```

`main_with` — это весь стандарт `main`: он загружает `.env`, анализирует те же аргументы, создает среду выполнения и запускается. Хост со своей собственной средой выполнения вместо этого вызывает `gproxy::run_with(cli, channels)`.

```rust
// edge/src/lib.rs
#[cfg(target_arch = "wasm32")]
mod entry {
    use std::sync::Arc;

    use worker::{Context, Env, HttpRequest, event};

    #[event(fetch)]
    async fn fetch(
        request: HttpRequest,
        env: Env,
        ctx: Context,
    ) -> worker::Result<gproxy_host_edge::Response> {
        gproxy_host_edge::fetch_with(request, env, ctx, || vec![Arc::new(my_channel::Acme)])
            .await
    }
}
```

`fetch_with` — это весь обработчик выборки акций. Модуль Worker имеет ровно один `#[event(fetch)]`, поэтому Edge Crate зависит от `gproxy-host-edge` **без** его функции `entry`, которая объявляет стандартный обработчик. Замыкание выполняется один раз для каждого изолята, когда его собирает первый запрос.

На обоих хостах канал, `id` которого соответствует встроенному, **заменяет** встроенный, так и поставляется исправленная копия существующего канала.

<a id="dependencies"></a>

### Зависимости

Зависит от извлечения gproxy по пути в версии, на которой вы строите:

```toml
# channel/Cargo.toml
[dependencies]
gproxy-channel = { path = "../../gproxy/crates/gproxy-channel" }
gproxy-protocol = { path = "../../gproxy/crates/gproxy-protocol", features = ["exhaustive"] }
http = "1"
serde = { version = "1", features = ["derive"] }
serde_json = "1"
```

```toml
# native/Cargo.toml
[dependencies]
my-channel = { path = "../channel" }
gproxy = { path = "../../gproxy/crates/gproxy", features = ["channels", "memory", "fs", "embedded-console"] }
```

```toml
# edge/Cargo.toml
[lib]
crate-type = ["cdylib", "rlib"]

[target.'cfg(target_arch = "wasm32")'.dependencies]
my-channel = { path = "../channel" }
gproxy-host-edge = { path = "../../gproxy/crates/gproxy-host-edge", default-features = false, features = ["channels", "d1", "libsql"] }
worker = { version = "0.8", default-features = false, features = ["http"] }
```

```toml
# Cargo.toml, the workspace root
[workspace]
resolver = "3"
members = ["channel", "native", "edge"]

# Copied from the checkout's root Cargo.toml: a patch applies only in the
# workspace that declares it, and the build depends on these.
[patch.crates-io]
sqlx-sqlite = { path = "../gproxy/vendor/sqlx-sqlite" }
btls-sys = { git = "https://github.com/0x676e67/btls", rev = "609f955e6de4df4a215ee9b273d327af1c0771db" }
```

Скопируйте `Cargo.lock` извлечения рядом с корневым `Cargo.toml` перед первой сборкой, чтобы разрешить версии зависимостей, с которыми тестировался gproxy.

Это проверка, а не зависимость от git, по одной причине: собственная консоль встроена в двоичный файл `crates/gproxy-host-axum/assets/web`, который не зафиксирован. Сначала запустите `pnpm install && pnpm build` в `console/` кассы или оставьте `embedded-console` вне функций для двоичного файла без него. В приведенной ниже сборке Worker консоль также взята из кассы.

Собственные списки функций `gproxy` и `gproxy-host-edge` работают так же, как и для стандартных сборок: `channels` — это каждый встроенный канал или назовите только те, которые используются при развертывании.

<a id="building-the-worker"></a>

### Создание Worker

`deploy/cloudflare` кассы собирает любой ящик Worker, а не только стандартный. Направьте его на свой абсолютный путь и разверните как обычно:

```sh
cd ../gproxy/deploy/cloudflare
pnpm install
GPROXY_EDGE_CRATE=/absolute/path/to/my-gproxy/edge pnpm run build
pnpm run deploy
```

При этом `worker-build` запускается в вашем ящике, удаляются разделы отладки и копируется Worker рядом с `wrangler.toml` кассы, активами консоли и их заголовками. Все в [руководство по развертыванию на периферии](/ru/deployment/edge/) — привязка D1, секреты, `GPROXY_CONFIG` — применяется без изменений.

**Канал для Worker должен быть создан для `wasm32-unknown-unknown`**, этому правилу уже следует каждый встроенный канал. На практике: нет сети `tokio`, нет файловой системы, `web-time`, а не `std::time::Instant`, и каждый запрос через клиент передает хост. Проверьте это с помощью `cargo check --target wasm32-unknown-unknown -p my-channel`.

<a id="what-the-public-contract-gives-you"></a>

### Что предоставляет публичный контракт

Все, что канал реализует или получает, является общедоступным в `gproxy_channel::channel`: `BaseChannel`, типы контекста и представления, каждая характеристика способности, типы дескрипторов и помощники, необходимые для запроса — `forwardable` и `HeaderAllowlist` для заголовков клиента, `insert_configured` для статического заголовка оператора, `strip_query_auth` для строки запроса и `standard_reason_observer`. Словарь протокола (`Dialect`, `Operation`, `OperationKey`, `HttpBody`, `WireRequest`) принадлежит `gproxy_protocol`.

`gproxy_channel::channels::shared` **не** общедоступен: он настроен на каналы в этом репозитории и изменяется вместе с ними. Скопируйте то, что вам нужно.

Приведенные выше правила применяются без изменений, особенно если подготовка является чистой, а аутентификация источника никогда не доходит до провайдера.

<a id="what-differs-from-a-built-in-channel"></a>

### Чем отличается от встроенного канала

- **Консоль отображает ваш канал на основе его дескриптора**, как и любой другой: форма провайдера из `config_keys`, форма учётных данных из `credential_kinds`, кнопки входа в систему из `login_modes`, элементы управления квотой, сбросом, обновлением и платным использованием из `capabilities`. Чего у него нет, так это доработки для каждого канала, написанной для встроенных идентификаторов — адаптированного текста подсказки, группы предустановок модели.
- **Самообновление отказывается устанавливаться** в собственном двоичном файле. Опубликованный выпуск — это сборка этого репозитория; его замена приведет к падению вашего канала и поломке каждого провайдера на нем при следующем перезапуске. Вместо этого перестройте новую версию. Проверка обновлений по-прежнему работает.
- **Контракт соответствует версии gproxy.** На практике изменения являются аддитивными — большинство типов протоколов — это `#[non_exhaustive]`, а новые методы `BaseChannel` поставляются со значениями по умолчанию — но строятся на основе используемой вами версии. Напишите `ChannelCapabilities { quota_query: true, ..Default::default() }`, а не перечисляйте каждое поле, чтобы новая возможность не сломала вашу сборку.

<a id="checklist-for-coding-agents"></a>

## Контрольный список для агентов кодирования

Те же шаги, что и агент должен их выполнить.

**Встроено** (запрос на извлечение здесь):

1. Считайте `crates/gproxy-channel/src/channels/nvidia.rs` (ключ API) или `codex/` (OAuth) в качестве шаблона, а также исходный код провайдера в разделе `samples/` или его ссылку на API.
2. Добавьте функцию в `crates/gproxy-channel/Cargo.toml`, линию в `channels!` в `src/channels/mod.rs` и функцию в каждый `cfg(any(...))` в `src/channels/shared/`, который использует канал.
3. Напишите `src/channels/<id>.rs` или `src/channels/<id>/`; переопределить `descriptor`.
4. Перенесите объект в четыре места шага 9.
5. Если канал поддерживает `allow_paid_usage` или обслуживает WebSocket, установите `paid_usage`/`websocket` в возможностях его дескриптора.
6. Добавьте переводы новых описаний дескрипторов/схем в `docs/src/i18n/reference/zh-cn.json` и `zh-tw.json`. Запустите `pnpm --dir docs generate:reference`; он экспортирует зарегистрированные каналы и отклоняет непереведенные описания. Не фиксируйте сгенерированный JSON.
7. Запустите команды под [Заканчивать](#finish).

**Вне этого репозитория**:

1. Скопируйте `examples/channel-plugin` из извлечения — `channel/` всегда, `native/` и `edge/` для развертываемых хостов. Добавьте вышеприведенный корень рабочей области `Cargo.toml` с его таблицей `[patch.crates-io]` и скопируйте `Cargo.lock`.
2. В `Cargo.toml` каждого ящика дайте пакету свои собственные `version` и `edition = "2024"` вместо ключей `*.workspace = true` и превратите каждую зависимость `workspace = true` в зависимость пути, показанную выше.
3. Переименуйте пакеты, двоичный файл, структуру и `ID`. Выберите идентификатор, который не будет использоваться встроенными средствами, если только цель не состоит в его замене.
4. Реализовать только против `gproxy_channel::channel`; не тянитесь к `channels::shared`.
5. `cargo clippy --all-targets -- -D warnings`; для Worker также `cargo check --target wasm32-unknown-unknown -p <channel> -p <edge>`.
6. Запустите собственный двоичный файл на свежем `GPROXY_DATA_DIR` или Worker под `wrangler dev --local` из `deploy/cloudflare` после сборки, указанной выше, и убедитесь, что `GET /admin/api/channels` указывает идентификатор.
