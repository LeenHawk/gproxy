<a id="the-gateways-own-routes"></a>

## Собственные маршруты шлюза

Четыре, и все остальное попадает в плоскость данных. Это противоположно обычному расположению, и оно намеренно: собственные маршруты шлюза представляют собой короткий известный список, а все остальное — чужие API, которые пересылает этот экземпляр. Новая поверхность провайдера не должна требовать здесь нового маршрута.

| Метод | Путь | Что это такое |
| --- | --- | --- |
| `GET` | `/healthz` | живость и опубликованная ревизия конфигурации; **не авторизован** |
| `GET` | `/publications/{id}` | опубликованный орган. Идентификатор **является** учётными данными, поэтому ключ не запрашивается |
| — | `/admin/api/…` | API оператора |
| — | `/portal/api/…` | API личного кабинета |
| — | все остальное | резервный вход |

```sh
curl -s http://127.0.0.1:8787/healthz
```

```json
{"revision":2,"status":"ok"}
```

`/healthz` считывает опубликованный снимок и не затрагивает ни базу данных, ни кеш, поэтому опрашивающий его балансировщик нагрузки не может сам стать нагрузкой, которая его откажет.

<a id="the-order-of-ingress"></a>

## Орден Ингресса

1. **CORS и адрес клиента.** Здесь отвечают на предполетный запрос и никогда не пересылают — он спрашивает этот экземпляр, что он примет, а у провайдера нет мнения по этому поводу. Адрес клиента разрешается в [правило доверенного прокси](/ru/reference/configuration/#the-trusted-proxy-rule) до того, как что-либо сможет его зарегистрировать.
2. **Маунт** — какой участок пути принадлежит этому шлюзу.
3. **Издатель OAuth**, по адресу `{mount}/v1/oauth/…`, перед плоскостью данных, поскольку эти пути относятся к *этому* экземпляру и отвечают в другом конверте ошибок.
4. **Маршрут обслуживания провайдера канала** — `/backend-api/…` Codex, `/api/…` кода Claude. Только при монтировании провайдера или пространства имен: для соответствия требуется канал, а для агрегированных имен монтирования — нет.
5. **Плоскость данных**, ниже.
6. **Консоль** с резервным вариантом SPA, расположенная за переключателем конфигурации.

Все, что доходит до конца, — это 404.

<a id="who-can-reach-a-file-or-video"></a>

### Кто может получить доступ к файлу или видео

Идентификаторы файлов и видео принадлежат провайдеру, а одни учётные данные провайдера обычно используются многими клиентами API, поэтому шлюз ведет собственный учет того, кто что создал. Успешная загрузка или создание видео записывается для клиента API (каждый сеанс ключа и консоли одного пользователя считается одним клиентом API; каждый грант OAuth является собственным клиентом API) и учётными данными, которые его обслуживали.

- Получение, загрузка, опрос или удаление идентификатора отвечает **404**, если этот клиент API не создал его через шлюз — тот же ответ, принадлежит ли идентификатор кому-то другому или не существует. Запрос отправляется на учётные данные, которые содержат ресурс.
- В списке отображаются только собственные элементы клиента API. Курсоры подкачки (`has_more`, `last_id`, `nextPageToken`) передаются без изменений, поэтому страница может содержать меньше элементов, чем `limit`, или ни одного, пока остается больше страниц; продолжайте пейджинг, пока провайдер не скажет, что их больше нет.
- Файлы и видео, созданные до существования этой проверки или непосредственно у провайдера, недоступны через шлюз.
- *возобновляемая* загрузка Gemini (то, что SDK google-genai использует по умолчанию) работает как обычно: `x-goog-upload-url`, с которого начинается ответ, является шлюзом URL, привязанным к клиенту API, байты передаются в сеанс провайдера с теми же учётными данными, а готовый файл является файлом клиента API. Другой клиент API сообщает, что URL получает **404**. За прокси-сервером установите `public_base_url` (или перенаправьте `Host` и доверенный `X-Forwarded-Proto`), чтобы имена URL доходили до адресов клиентов.
- То же правило распространяется на файлы, на которые ссылаются другие запросы: `file_id` в чате, ответах или сообщении Claude (включая `file_ids` контейнера интерпретатора кода), Gemini `fileData.fileUri`, называющий файл Files API, видео `input_reference`. Файл, который клиент API не загрузил, отвечает **404** перед отправкой чего-либо, и запрос выполняется с использованием учётных данных, содержащих файлы; файлы, загруженные с использованием двух разных учётных данных, не могут использоваться в одном запросе (**400**). Аналогично проверяются составные формы (поля `file_id`, `file_ids[]`, `input_reference[file_id]`).
- В WebSocket ответов новый ответ открывает соединение с провайдером на учётных данных, содержащих файлы, на которые он ссылается; продолжение (`previous_response_id`) остается в его учётной записи, поэтому файлы, загруженные в другое место, отклоняются с помощью события `error` — начните новый ответ, чтобы использовать их.
- В сокете Realtime или Gemini Live сообщение клиента с именем файла, которым клиент API не владеет в учётных данных сокета, не пересылается: Realtime отвечает событием `error` (`file_not_found`), Gemini Live закрывается с кодом `1008`.

Standard Realtime и GPT-Live используют разные протоколы и права учётной записи. Устаревшие маршруты `/v1/live` остаются для совместимости. Новые маршруты Live и создание собственного голоса — это ключевые возможности OpenAI API; Codex поддерживает стандарт Realtime, секреты клиента и явное зависание. Сама по себе загрузка сеанса 201 не доказывает, что сеанс может работать. Секреты клиента — это учётные данные носителя провайдера для прямых подключений. Их тела никогда не перехватываются, а запросы выполняются напрямую провайдером в обход шлюза допуска и измерения. Явное зависание и побочные полосы используют область создания API-клиента и исходные учётные данные. Их связанная модель восстанавливается перед допуском, включая проверку разрешений текущей модели.


В ответах используется тот же путь `/v1/responses` для HTTP, POST и WebSocket GET. Его рукопожатие подтверждает подлинность клиента API; каждый `response.create` затем предоставляет модель разрешений, маршрутизации и ограничений генерации. Независимые линии `stream_id` могут работать одновременно. Новая цепочка реагирования может выбрать новую цель; Продолжения `previous_response_id` сохраняют свою первоначальную цель. Соединения Idle Responses не имеют разрешений на параллелизм генерации.

Сокеты Native Responses перенаправляют элементы управления провайдера. Мосты HTTP к ответам, чату, Claude и Gemini поддерживают прогрев локального контекста, прерывание, управление преемниками и ввод входных данных между сегментами генерации HTTP. Локальная прогрев не выполняет предварительное заполнение кэша провайдера. История `store:false` сохраняется только для клиентского подключения; сохраненные продолжения сохраняют историю области действия и целевые привязки. Начатые или неопределенные генерации не воспроизводятся на другой цели.

`POST /v1/realtime/calls` — это многочастный запрос HTTP, содержащий предложение SDP, а продолжающее его рукопожатие не несет **вообще никакого тела**. Что сохраняется при обновлении, так это идентификатор вызова — в пути или в `?call_id=` — который движок ищет, чтобы привязать сокет к учётным данным аутентификации, которые ответили на предложение. Именно по этой причине запрос пересылается без изменений.

Сеанс реального времени **никогда не преобразуется**: только передача на том же диалекте, поскольку клиент, который может продолжать говорить в середине ответа, не имеет эквивалента на полудуплексном диалекте.

**Перед обновлением допускается режим реального времени.** Аутентификация, затем форма рукопожатия, затем вход, затем рукопожатие провайдера; `101` записывается последним. Таким образом, каждый отказ является ответом HTTP, который клиент может прочитать — сокет, который принят и немедленно закрыт, не несет ни статуса, ни тела, ни кода. **Отказ в рукопожатии провайдера передается дословно**: `429 {"error":{"code":"insufficient_quota"}}` провайдера стоит больше, чем любой 502, который этот шлюз мог изобрести.

Сокет реального времени удерживает свою аренду параллельного доступа до тех пор, пока он не **закроется**, а не до тех пор, пока не будет записан `101`. Сеанс, продолжающийся час, удерживает свой слот на этот час.

<a id="codex-only-routes"></a>

### Маршруты только для Codex

Частные операции Codex требуют монтирования провайдера с использованием канала Codex. Для провайдера с именем `codex` используйте `POST /codex/v1/memories/trace_summarize`. Они используют допуск к нормальной работе, маршрутизацию модели и расчет; общий API `/v1` их не предоставляет. Стандартный `/v1/moderations` использует собственный контракт `create_moderation` JSON.

Службы учётной записи также доступны под `/codex/v1`, включая `usage/thread_usage/query_v2` (POST), `usage/plan_limit_history`, а также ежедневные отчеты о токенах, кредитах, рабочей области, плагинах и навыках (GET). Собственные псевдонимы `/codex/api/codex/**`, `/codex/backend-api/**` и `/codex/ps/**` остаются доступными. Администраторы могут читать отчеты провайдера выбранной учётной записи с помощью `x-gproxy-view: credential:<id>`. Представления клиента API и пула явно помечают отсутствующие исторические резервы и учет кредитов провайдеров как недоступные с помощью сумм null, вместо того, чтобы заимствовать данные счета или сообщать о сфабрикованных нулях.

<a id="the-ambiguous-paths"></a>

### Неоднозначные пути

`/v1/models`, `/v1/models/{id}` и `/v1/files` пишутся одинаково в OpenAI, Claude и Gemini поверхности v1, и диалект решает, для каких типов протокола требуется преобразование, поэтому если угадать неправильно, это преобразованное тело, которое клиент не сможет проанализировать.

Тайбрейком является **собственный заголовок аутентификации клиента** — `x-goog-api-key` — это Gemini, `anthropic-version` — это Claude, — что является свидетельством того, что клиент предоставил информацию о себе, а не значение по умолчанию, изобретенное этим шлюзом. При отсутствии доказательств побеждает первая строка, и таблица упорядочивается так, что это OpenAI.

<a id="the-mount-grammar"></a>

## Гора Грамматика

| Путь | Устанавливать | Сужается до |
| --- | --- | --- |
| `/v1/messages` | агрегированный | ничего |
| `/acme/v1/messages` | пространство имен `acme` | выставленные имена под `acme/` |
| `/openai-prod/v1/messages` | провайдер `openai-prod` | этот провайдер |

**пространство имен** — это первый сегмент открытого имени модели, содержащего косую черту. Монтирование **provider** называет `name` провайдера — метку оператора, а не идентификатор строки, поскольку никто не вводит машинно созданный идентификатор в базу URL клиента. Пространство имен выигрывает у одноименного провайдера.

**Префикс удаляется только тогда, когда то, что осталось, также является объявленной поверхностью.** Любое упрощение этого правила неверно: провайдер с именем `backend-api` в противном случае съел бы `/backend-api/codex/responses`, который является реальным путем Codex, и превратил бы вызов плоскости данных в несуществующее монтирование.

**Поэтому неоднозначный путь разрешается в сторону агрегированного монтирования.** Если первый сегмент называет что-то, а остальная часть не является поверхностью, обслуживаемой этим шлюзом, путь остается целым. Потеря крепления — это ошибка 404, которую может увидеть оператор; Взять тот, который не был предусмотрен, — это запрос, отправленный не тому провайдеру.

Монтирование сужается за счет **префикса имени модели**, который является собственной грамматикой преобразователя, а не вторым правилом. Имя, которое уже содержит префикс, остается в покое.

:::note[Один известный пробел] Операция **без модели** при монтировании провайдера сужается до *канала* этого провайдера, а не провайдера. `GET /p1/v1/models` перечисляет модели каждого провайдера на канале `p1`, к которым может обратиться клиент API. Для его закрытия требуется поле, которого еще нет в форме запроса. :::

<a id="the-oauth-issuer"></a>

## Эмитент OAuth

Относительно префикса монтирования (`""`, `/acme`, `/openai-prod`):

```text
GET  {prefix}/v1/oauth/authorize    consent handoff (302 to `/console/authorize` for a browser)
POST {prefix}/v1/oauth/authorize    the person's decision
POST {prefix}/v1/oauth/token        code, refresh and device grants
POST {prefix}/v1/oauth/device/code
POST {prefix}/v1/oauth/revoke
GET  {prefix}/v1/.well-known/oauth-authorization-server
GET  /.well-known/oauth-authorization-server{prefix}/v1   (RFC 8414 §3.1)
```

Идентификатор издателя — `{origin}{prefix}/v1`, поэтому агрегированное монтирование — `https://host/v1`, а не `https://host`: тогда одно правило производит все три монтирования. RFC 8414 требует, чтобы идентификатор был именно тем идентификатором, из которого клиент получил документ, и только хост знает, на какое монтирование поступил запрос, поэтому он передается, а не вычисляется.

v3 обслуживал их в корне. Перемещение их под `/v1` сделало правило префикса таким же, как и `/v1/messages`, и этот шаг был дешевым, потому что v3 вообще никогда не реализовывал конечную точку обнаружения — клиенты все равно жестко кодировали адрес.

<a id="management-routes"></a>

## Маршруты управления

Каждое семейство имеет одни и те же шесть маршрутов, сгенерированных из одного объявления, поэтому в семействе не может случайно оказаться пять из них:

```text
GET    /admin/api/{family}           list      (page and filters in the query)
POST   /admin/api/{family}           create
GET    /admin/api/{family}/{id}      get
PATCH  /admin/api/{family}/{id}      update
DELETE /admin/api/{family}/{id}      delete    → 204
POST   /admin/api/{family}/batch     batch
       [{"create": …}, {"update": {"id": …, "patch": …}}, {"delete": "id"}]
```

Пакет — это одна фиксация ревизии, сколько бы строк она ни называла: либо каждый элемент является долговечным, либо ни один из них не является долговечным.

**Идентификационные** семейства: `users`, `api-keys`, `organizations`, `teams`, `permissions`, `rate-limits`. Членство в организациях и командах имеет свои собственные конечные точки. `oauth-clients` имеет `POST …/{id}/retire` вместо удаления — гранты, выданные клиентом, по-прежнему называют его. В своем пакете удаление удаляется, а пакет, который удаляется, содержит только удаления: удаление — это его собственная транзакция, поэтому он не может использовать фиксацию совместно с созданиями или исправлениями. Вышедший из эксплуатации `client_id` можно зарегистрировать снова; новая регистрация повторно использует строку, а отозванный грант остается отозванным. Пакет `api-keys` отказывает в создании, поскольку создание ключа отвечает открытым текстом, которому пакету некуда возвращаться. Пакет `users`, в котором не остается ни одного включенного администратора, полностью отклоняется.

Семейства **конфигураций**:

`providers`, `credentials`, `models`, `provider-models`, `routes`,
`route-members`, `connection-profiles`, `rule-sets`, `rules`,
`provider-rule-sets`, `operation-rules`, `operation-endpoints`, `quotas`,
`price-rules`, `price-rates`, `price-tiers`.

Помимо шести: `settings`, операции с учётными данными (`reveal`, `status`, `refresh`, `quota`, `quota-probe`, `quota-reset`, `health-reset`, `limits`), `models/{discover,discover/apply,test}`, `rule-sets/{id}/rules`, `rule-sets/{id}/rule-presets/{preset}`, `providers/{id}/routing-defaults/reset`, `quotas/status`, `quotas/{id}/{reset,limit-reset}`, `export`, `import`, `connectivity/test`, `channels`, `tls-presets`, `rule-presets`, `default-model-catalog`, `tokenizer-vocabs`, `tokenizer-auth`, `session`, `sessions` и `audit`.

Полезные данные и поведение управления изменились в версии 4; проверьте старые скрипты на соответствие текущему API. См. [Использование, журналы и аудит](/ru/guides/observability/) для получения информации о конечных точках истории всего экземпляра.

<a id="portal-routes"></a>

## Портальные маршруты

```text
POST   /portal/api/login             name + password → session cookie and token
POST   /portal/api/logout
GET    /portal/api/context           the caller, their memberships, their features
GET    /portal/api/models            every exposed name, each marked `permitted`
GET    /portal/api/usage             their own spend
GET    /portal/api/quota             their own budget windows
GET    /portal/api/requests          their recent requests, if enabled
GET    /portal/api/sessions
GET    /portal/api/keys              (+ POST, DELETE …/{id}, POST …/{id}/rotate, GET …/{id}/secret)
GET    /portal/api/oauth-sessions    (+ DELETE …/{id})
POST   /portal/api/password
GET    /portal/api/oauth/device      a pending device code (?userCode=), for `/console/device`
POST   /portal/api/oauth/device      approve or deny it; a session or a management key
```

Для защиты требуется аутентифицированный API-клиент и **ничего больше**. Проверка роли отсутствует, поскольку проверять нечего: каждая операция портала ограничена API-клиентом, на основе которого она была создана, и ни одна из них не принимает идентификатор пользователя. Чек можно забыть; отсутствующий параметр не может.

`login` и `logout` находятся вне защиты — первый запускается до появления API-клиента, а второй должен работать для сеанса, срок действия которого уже истек, или в браузере остается файл cookie, который он никогда не сможет удалить.

<a id="resolution-and-the-failover-budget"></a>

## Разрешение и бюджет аварийного переключения

См. [Модели, маршруты и открытые имена](/ru/guides/models/), чтобы узнать о четырех формах имен и их порядке. Бюджет:

- это собственный маршрут `maxAttempts`, ограниченный `settings.maxAttempts`;
- он **распределяется между целевыми объектами**: каждому целевому объекту предоставляется не более столько попыток, сколько у него есть учётных данных, и не больше, чем то, что осталось, поэтому план не может стоить больше вызовов провайдера, чем его бюджет;
- сбой переходит к следующему провайдеру **только если другой провайдер может его обслужить** — нет пригодных для использования учётных данных, недействительные учётные данные, продолжение закреплено где-то еще, любая ошибка канала или транспорта или ответ 401, 403, 429 или 5xx;
- израсходованный бюджет, запрещенный запрос, отмена, плохая конверсия и сбой хранилища или кэша останавливают вызов на месте;
- если цели не осталось, **последний ответ возвращается в его нынешнем виде**. Код 429 от конечного провайдера — это код 429 клиента API, а не синтезированная ошибка.

Тело запроса буферизуется один раз, чтобы его можно было воспроизвести. Потоковое тело через `maxRequestBodyBytes` остается потоком, и план ограничивается одной целью: большую загрузку не стоит считывать в память ради аварийного переключения.
