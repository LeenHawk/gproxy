Три точки расширения хранилища, выбираемые независимо: **база данных**, **кэш** и необязательное **содержимое файла**.

<a id="the-database"></a>

## База данных

| `GPROXY_PERSISTENCE` | Связь | Построить |
| --- | --- | --- |
| `sqlite` *(по умолчанию)* | `<data-dir>/gproxy.db` или путь / `sqlite://` URL в `--dsn` | всегда компилируется в |
| `postgres` | `postgres://…` в `--dsn` | `--features postgres` |
| `mysql` | `mysql://…` в `--dsn` | `--features mysql` |
| D1 | привязка Cloudflare | хост Workers |
| libSQL/Турсо | по трубопроводу Грана HTTP | `--features libsql` |

MySQL требует версии 8.0.13 или новее для выражений по умолчанию JSON. Драйверы PostgreSQL и MySQL включают поддержку TLS.

`--dsn` называет свой собственный бэкэнд, когда `--persistence` отсутствует, поэтому схемы обычно достаточно.

**Бэкэнд, которого нет в этой сборке, отклоняется при запуске**, указывая функцию, которая его предоставит, а не по первому запросу.

```sh
gproxy serve --dsn 'postgres://gproxy:…@db.internal:5432/gproxy'
```

libSQL — это вариант для хоста, у которого нет D1 — например, Netlify — потому что половина HTTP предоставляется собственным транспортом клиента API и, следовательно, работает на каждой цели.

<a id="one-api-over-all-of-them"></a>

### Один API над всеми ними

Собственные соединения SeaORM и Cloudflare D1 используют **один** магазин API. Каждый метод доступа к сущности проходит через один общий репозиторий, поэтому обычный CRUD не пишется вручную для каждой таблицы, и каждый метод выполняет **один атомарный пакет**.

Создание хранилища не открывает базу данных и не изменяет схему.

Два последствия, которые стоит знать:

- При чтении сохраняется порядок ввода, дубликаты и `None` для отсутствующего идентификатора, поэтому клиент API может заархивировать результат обратно в свой запрос.
- Ключевой предикат разделяется в соответствии с ограничением D1 на 100 операторов привязки **в пределах одного пакета**. Произвольный клиент API SQL не разделяется, и ограничения на запросы и размеры базы данных по-прежнему применяются.

Ошибки SQL откатывают транзакционные записи. Условная запись нулевой строки возвращает конфликт, а не откатывает остальную часть пакета. **Автоматическая повторная попытка отсутствует**: неоднозначный результат фиксации означает, что сначала необходимо проверить устойчивое состояние.

<a id="schema-synchronization"></a>

### Синхронизация схемы

```text
$ gproxy migrate --data-dir ./data
INFO gproxy::instance: schema is up to date warnings=0
```

Синхронизация осуществляется **сначала объект**, а не по нумерованной лестнице миграции: один реестр описывает таблицы, а синхронизация создает недостающее в новой базе данных и постепенно добавляет поддерживаемые недостающие столбцы и индексы в существующую. Повторные вызовы сохраняют строки.

`serve` тоже делает это. Отдельная команда существует для развертывания, которое запускает ее как отдельный шаг, **с одним автором**, перед запуском любого экземпляра — а это то, что требуется для более чем одного экземпляра в одной базе данных.

Чего **не** делает синхронизация: она не создает настройки по умолчанию или администраторов, не выполняет версионную миграцию и не преобразует тип столбца, его данные или существующий внешний ключ. Для этого требуется явная миграция, и нет никакой гарантии наличия одной атомарной транзакции для каждого встроенного бэкэнда.

Отчет содержит предупреждения — например, о различиях типов D1 — и пустой список **не является доказательством** того, что все изменения были применены. Прежде чем считать запуск завершенным, прочтите диагностику.

<a id="exact-amounts"></a>

### Точные суммы

Деньги и лимиты хранятся в виде масштабированных целых чисел, а не чисел с плавающей запятой. Один атом — `0.000000001`, а представимый диапазон — около ±9,2 миллиарда.

Столбцы SQL — это `BIGINT`, а сущности переносят атомы в виде текста через границу JavaScript D1, так что сравнения, упорядочивание и сложение остаются в базе данных числовыми. JSON использует десятичные **строки** по той же причине.

Арифметические операции выполняются в десятичном виде и округляются **один раз** для полного расчета, привязываясь к четному. Расчет проверяет наличие отрицательных значений и знаковое переполнение, прежде чем увеличивать счетчик.

<a id="the-cache"></a>

## Кэш

| Бэкэнд | Выбрано | Область применения |
| --- | --- | --- |
| Память *(изначально по умолчанию)* | `--features memory` | один процесс |
| Редис / Валки | `GPROXY_REDIS_URL` | общий |
| База данных | автоматически на Wasm, настраивается в другом месте | общий доступ через одну и ту же базу данных |

Кэш содержит состояние TTL, точные счетчики, разрешения и аренду, а также тему аннулирования. В нем **нет** коммерческих предприятий и **нет** долгосрочного реестра.

| Операция | Семантика |
| --- | --- |
| `get` / `put` / `delete` | непрозрачные байты, обязательный положительный TTL, новая версия при каждом размещении |
| `compare_exchange` | ожидаемая версия или отсутствие; заменить или удалить |
| `counter` / `increment` / `decrement` | точные неотрицательные целые числа с проверкой атомарного потолка |
| `acquire_permit` | не более N живых холдеров, каждый со своим TTL |
| `acquire_lease` | тот же домен с лимитом 1 — обновление аренды |
| `publish` / `subscribe` | подсказки о недействительности с потерями |

Операции выполняются атомарно **для каждого ключа**, а не между ключами. Домены «ключ-значение», счетчик, разрешение и тема являются отдельными, поэтому в каждом из них может существовать одно и то же логическое имя.

Счетчик имеет **фиксированное окно**: только его создание устанавливает TTL, поэтому каждый экземпляр согласовывает границу только на основе часов. Разрешение **не** привязано к окну — оно измеряет запросы в процессе, которые не разделяет граница, и его период — это всего лишь то, как долго кэш ожидает, прежде чем забрать один из запроса, который умер, не освободив его.

<a id="failure-is-a-refusal-never-a-local-fallback"></a>

### Неудача — это отказ, а не локальный запасной вариант

Сбой Redis **не** приводит к незаметному переходу в кэш внутри процесса. Два экземпляра, каждый из которых откатывается, будут удерживать противоречивые блокировки и дважды учитывать один и тот же предел, что хуже, чем ошибка.

Запрос с ограничением скорости, на который кэш не может ответить, **отклоняется с кодом 429**. Его передача приводит к тому, что сбой в работе кэша приводит к тому, что «все ограничения на экземпляре отключены» — тот самый момент, который нужен злоумышленнику, а оператор не видит.

<a id="what-needs-a-shared-one"></a>

### Что нужно общего

Для запуска более одного экземпляра требуется Redis или кэш на базе базы данных. Без него каждый экземпляр подсчитывает свои собственные лимиты запросов, каждый обновляет один и тот же токен OAuth, и ни один экземпляр не видит недействительности конфигурации других.

Сеанс входа также находится в кеше, а не в процессе, что позволяет любому экземпляру завершить вход в систему, начатый другим — за балансировщиком нагрузки обычно находится другой.

Для развертывания с отдельными средами предоставьте каждой из них собственное пространство имен Redis. Канал уведомлений явно кодирует номер базы данных, поскольку сам Redis Pub/Sub игнорирует `SELECT`.

<a id="the-database-as-a-cache"></a>

### База данных как кэш

Для хоста без резидентного процесса и без Redis (граничная изоляция D1 или libSQL) кэш может состоять из трех таблиц в самой базе данных. Срок действия сравнивается в SQL, поэтому узлы одной базы данных договариваются о том, что является активным.

Он не передает **транспорт уведомлений**: подписка дает начальную подсказку о повторной синхронизации, а затем ничего, поэтому такой хост догоняет свое собственное расписание. Вот и вся синхронизация хоста Workers: одна ревизия считывается в начале каждого запроса.

<a id="configuration-synchronization"></a>

## Синхронизация конфигурации

```text
commit_revision([statements…, config_revision += 1, read back])   one transaction
      ↓
reload   this instance's snapshot
      ↓
publish  ConfigurationChanged { revision, scopes }
```

Два механизма, потому что ни одного недостаточно:

| | несет | Не удалось |
| --- | --- | --- |
| аннулирование общего кеша | «посмотри еще раз», в течение миллисекунд | потеря сообщений |
| опрос `settings.config_revision` | непреходящая истина, каждые 30 секунд | быть медленным |

Уведомление никогда не содержит состояния. Он сообщает, какая ревизия существует, и экземпляр перезагружается только тогда, когда он опережает ту, которую он обслуживает. Нечитаемая полезная нагрузка скорее перезагружается, чем угадывает.

**Собственный счетчик кэша не может заменить ревизию базы данных.** При перезапуске или вытеснении Redis он может быть потерян, а две независимые фиксации — одна в базе данных, одна в теме — не становятся транзакцией, поскольку находятся рядом.

Перезагрузки сериализованы и монотонны: более старая ревизия никогда не заменяет более новую, а при неудачной перезагрузке сохраняется предыдущий снимок.

<a id="file-storage"></a>

## Хранение файлов

Необязательно и отключено, если не выбран серверный интерфейс.

| Бэкэнд | Выбрано | Родной | Workers |
| --- | --- | --- | --- |
| Локальная файловая система | `--features fs` + `--file-storage-dir` | да | нет |
| Совместимость с S3-, включая R2 | `--features s3` + блок `[file_storage]` | да | да |

Он содержит опубликованные тела — байты, стоящие за `/publications/{id}`, — и загруженные словари токенизатора. **Метаданные файла и право собственности остаются в базе данных**; уровень хранения содержит контент и ничего больше.

Если хранилище файлов не настроено, публикация и выборка словаря отвечают «не поддерживается»: байты некуда помещать.

Ссылка на публикацию также требует `GPROXY_PUBLIC_BASE_URL`. Если ничего не настроено, публикация завершается неудачно *до* записи любого тела, и клиенту API предлагается запросить встроенные байты. Создание ссылки на основе `Host` запроса, выбранного клиентом, было бы хуже, чем отсутствие ссылки: ответ провайдера принимается, байты сохраняются, URL выдается, и возникает ошибка 404 где-то еще.

<a id="backups"></a>

## Резервные копии

- **SQLite** — остановите процесс и скопируйте `<data-dir>/gproxy.db` или используйте собственную онлайн-резервную копию SQLite. **Сохраняйте мастер-ключ вместе с копией**: без него зашифрованную базу данных невозможно прочитать.
- **PostgreSQL и MySQL** — собственные инструменты дампа базы данных.
- **D1, libSQL/Turso** — снимки платформы.
- **Логично** — `gproxy export --out config.json --include-secrets`. Он содержит *конфигурацию*, а не историю: личность, использование и захваты намеренно исключены из нее. См. [Конфигурация](/ru/reference/configuration/#moving-a-configuration).

Зашифрованный большой двоичный объект привязан к идентификатору своей строки, поэтому восстановление секрета одной строки в другой строке не работает — это свойство безопасности, а не препятствие для восстановления всей базы данных.
