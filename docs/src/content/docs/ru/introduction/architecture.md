v4 — это переписанная версия v3. Работа та же; структуры нет. Эта страница представляет собой карту: ящики, швы между ними и правила, которые удерживают конструкцию от смещения назад.

Единственное предложение, которое объясняет все остальное: **каждый уровень решает ровно один класс вопросов и выдает суженный ответ, который не открывается ни в одном из нижних уровней.**

<a id="the-two-assemblies"></a>

## Две Ассамблеи

```text
sdk  =  engine + configuration writes + login + resolution + queries + sync
app  =  sdk + identity and admission + the typed admin / portal / issuer operations
host =  app + a transport
```

`gproxy-sdk` — встраиваемая ручка. Он собирает движок из реализаций по умолчанию, владеет записями конфигурации, которые развивают `settings.config_revision`, превращает имя входа в строку учётных данных, преобразует имя модели в план выполнения и сохраняет каждый экземпляр развертывания в одной и той же версии. Он не содержит **нет сервера HTTP и никакой идентификации**.

`gproxy-app` добавляет, кто звонит и к чему они могут обращаться: пользователи, ключи API шлюза, организации, команды, разрешения, лимиты запросов, эмитент OAuth, аудит и операции, которые записывают любые из них. У него **нет сервера** — нет маршрутизатора, нет среды выполнения, нет CLI — что позволяет одним и тем же решениям работать как на собственном сервере Axum, так и внутри Cloudflare Worker.

Хост — это тонкий остаток: входящие байты, вводимые вызовы, байты обратно.

## Ящики

| Ящик | держит | Никогда |
| --- | --- | --- |
| `gproxy-protocol` | Моделирование соединений (`WireRequest`, `WireResponse`, корпуса, каркас, розетки), реестр операций, типы протокола OpenAI / Claude / Gemini, а также потребности в адаптации протокола интерфейсов с возможностями хоста. | Знает, что канал существует; соответствует пути URL |
| `gproxy-channel` | `BaseChannel`, дополнительные характеристики способностей и адаптеры провайдеров, лежащие в основе функций Cargo. | Зависит от двигателя или магазина; выбирает транспортный сервер |
| `gproxy-client` | Исходящий транспортный контракт и его реализации `reqwest`/`wreq`, а также серверные части Wasm `fetch` и Workers. | Считывает базу данных, выбирает учётные данные, преобразует протокол |
| `gproxy-core` | Механизм: снимок выполнения провайдера, выбор учётных данных, обновление и работоспособность внутри разрешенного набора, преобразование, перезапись, бюджеты, цены, расчеты и наблюдение. | Разрешает маршрут, проверяет разрешение, запускает сервер |
| `gproxy-store` | Схема и ее запросы, серверная часть по функциям | — |
| `gproxy-cache` | Состояние TTL, атомарные счетчики, разрешения и аренда, аннулирование перекрестных экземпляров; Память и Redis | хозяйствующие субъекты; тихий локальный резервный вариант при сбое серверной части |
| `gproxy-seaorm` | Пакетное чтение и запись SeaORM, привязка D1, сопоставление типов, синхронизация схемы. | Субъекты предпринимательства |
| `gproxy-tokenizer` | Строка для подсчета токенов в соответствии с локальным общим словарем | Парсинг запросов, скачивание, фоновая работа |
| `gproxy-file` | Дополнительное локальное хранилище контента или хранилище контента S3/R2 через OpenDAL. | Метаданные файла; собственность |
| `gproxy-sdk` | Ручка: сборка, `manage()`, `login()`, разрешение, сессии, `call()`, `query()`, `sync` | Любой код сервера HTTP; любая идентичность |
| `gproxy-app` | Идентичность, допуск, две поверхности продукта и эмитент. | Транспорт |
| `gproxy-host-axum` | HTTP путь → операция. Таблица маршрутов | Собственное решение по продукту |
| `gproxy-host-edge` | `fetch` → маршрутизатор axum | Вторая таблица маршрутов |
| `gproxy-host-tauri` | IPC → работа, только для панелей управления и пользователя. | Плоскость данных |
| `gproxy` | Командная строка: среда, файл, сокет, терминал | Все, что могла сделать библиотека |

Стрелки указывают в одну сторону. Хост зависит от приложения, приложение от SDK, SDK от движка. Движок никогда не получает прослушиватель, маршрутизатор или UI.

<a id="where-each-question-is-answered"></a>

## Где есть ответ на каждый вопрос

| Вопрос | Ответил |
| --- | --- |
| кто звонит | Аутентификатор `gproxy-app` |
| чего они могут достичь и чьи это деньги | Прием `gproxy-app` |
| какой провайдер обслуживает это название модели | преобразователь SDK |
| какие учётные данные и что делать в случае сбоя | двигатель |
| что за операция *делает* | Семейства операций `gproxy-app` и `manage()` SDK |
| какой сбой стоит на проводе | `AppError::status_code` / `code` |
| какой URL означает какую операцию | хост аксум |

Хост, который повторно ответил на любой из первых пяти вопросов, применил бы свой ответ к HTTP, а не к IPC, а это именно тот класс ошибок, для предотвращения которого существует шов.

<a id="resolution-and-the-plan"></a>

## Резолюция и план

Разрешение происходит **до** движка, поэтому движок видит только уже решенную цель. Имя модели соответствует первому применимому правилу:

| Имя | решает | Попытка бюджета |
| --- | --- | --- |
| отсутствующий | каждый включенный провайдер, без модели провайдера | `settings.max_attempts` |
| открытое название модели | включенные участники этого маршрута | собственный маршрут |
| `provider/model` | тот самый провайдер | `settings.max_attempts` |
| что-нибудь еще | ошибка неизвестной модели | — |

Открытые имена совпадают точно и **перед** формой префикса, поэтому оператор может предоставить буквальное имя `openai/gpt-5`. Префикс всегда представляет собой имя провайдера, а не идентификатор канала.

Затем кандидаты сужаются по каналу, по разрешенным идентификаторам провайдеров и по разрешенным идентификаторам учётных данных — последнее — это то, как уровень продукта защищает учётные данные одной организации от запросов другой. Заказ — `(tier, health, descending weight, stable id)`; только ведущий забег сбалансирован в соответствии со стратегией маршрута.

<a id="failover-has-two-axes"></a>

## Отказоустойчивость имеет две оси

Механизм уже повторяет попытки с использованием учётных данных одного провайдера. SDK является другой осью и переходит к следующему провайдеру **только в случае сбоев, которые мог бы обслужить другой провайдер**: нет пригодных для использования учётных данных, недействительные учётные данные, продолжение закреплено в другом месте, любая ошибка канала или транспорта и ответ 401, 403, 429 или 5xx. Израсходованный бюджет, запрещенный запрос, отмена, неправильное преобразование и сбой хранилища или кэша — все это останавливает вызов, поскольку повторная попытка в другом месте будет стоить дороже.

Бюджет попыток распределяется между целевыми объектами, поэтому план не может стоить больше вызовов провайдера, чем его `max_attempts`. Если цели не осталось, последний ответ возвращается в его нынешнем виде — 429 от конечного провайдера — это 429 API-клиента, а не синтезированная ошибка.

<a id="one-write-one-revision-one-notification"></a>

## Одна запись, одна редакция, одно уведомление

```text
commit_revision([statements…, config_revision += 1, read back])   one transaction
      ↓
reload   the snapshot this instance serves
      ↓
publish  ConfigurationChanged { revision, scopes }
```

Строки и ревизия — это одна и та же транзакция. Разделите их, и откроются два настоящих окна: строки приземляются без неровностей, поэтому одноранговые узлы никогда не учатся перезагружаться, и изменения невидимы в каждом другом экземпляре; или удар приземляется без строк, поэтому каждый узел перезагружается даром.

Перезагрузка происходит **до** уведомления. В обратном порядке будет объявлено о ревизии, которую этот экземпляр еще не может обслужить. Само уведомление — это самое лучшее — кеш, который отказывается от него, стоит развертывания в один интервал опроса, поэтому опрос и существует.

Два механизма, потому что ни одного недостаточно:

| | несет | Не удалось |
| --- | --- | --- |
| аннулирование общего кеша | «посмотри еще раз», в течение миллисекунд | потеря сообщений |
| опрос `settings.config_revision` | непреходящая истина, каждые 30 секунд | быть медленным |

Перезагрузки сериализованы и монотонны; более старая версия никогда не заменяет более новую, а в случае неудачной перезагрузки предыдущий снимок остается в силе.

<a id="settlement-is-not-optional"></a>

## Урегулирование не является обязательным

Механизм гарантирует, что каждый путь, который достигает провайдера, проходит по одной и той же воронке: цена биржи, взимание платы за каждое применимое бюджетное окно, передача отчета наблюдателю. Вокруг него нет скоростного пути, потому что путь вокруг него - это безлимитный трафик.

То, что *необязательно*, задается **перед** работой, а не отбрасывается после нее. Отключенный захват ничего не выделяет и не клонирует тело; Соглашение v3 оплатило всю стоимость до того, как приемник смог ее отклонить.

Затраты рассчитываются после звонка провайдера, поэтому текущие и одновременные вызовы могут превысить бюджет. Расчет идемпотентен для каждого идентификатора запроса, и в случае сбоя расчета теряется учет, а не доставленный ответ.

Модель без правила ценообразования устанавливается на ноль с размером `unpriced = true`. Оператору нужен был сигнал, а не отказ.

<a id="wasm-is-a-target-not-a-fork"></a>

## Wasm — это цель, а не форк

`gproxy-app` строится для `wasm32-unknown-unknown`, как и маршрутизатор axum, поэтому `gproxy-host-edge` монтирует один и тот же `Router` вместо того, чтобы дважды записывать таблицу маршрутов. половинки сервера Axum — это функции Cargo, а не ящик; то, что не учитывается в сборке Wasm, имеет форму сокета и никогда не является маршрутом.

Настоящим препятствием был `Send`. На Wasm движком является `!Send` **по дизайну** — транспортный дескриптор JS принадлежит изоляту, который его создал, — в то время как axum хочет состояние `Send + Sync` и фьючерсы обработчика `Send`. Это исправляют два моста, проверенных во время выполнения, оба работают, потому что изолят Worker является однопоточным: приложение хранит свой дескриптор в `SendWrapper`, а хост axum оборачивает каждое тело обработчика. Обработчик, который забывает об обертке, является **ошибкой компиляции целевого объекта Wasm, назвавшего этот обработчик** — что является принудительной мерой и причиной того, что он находится в обработчике, а не за `cfg` на маршрутизаторе. Маршрут, который не может скомпилироваться для ребра, не может молча не существовать там.

<a id="rules-that-keep-it-this-way"></a>

## Правила, которые сохраняют это таким образом

- Движок никогда не зависит от серверной платформы, маршрутизатора или UI.
- Каждый запрос, поступающий к провайдеру, проходит через ту же воронку.
- Преобразование попарное; промежуточного представления нет, и преобразователь никогда не читает и не записывает пакет неизвестных полей.
- Запись конфигурации — это одна транзакция с ее ревизией.
- Публикация снимка монотонна; перезагрузка никогда не идет назад.
- Сборка никогда не дает сбоя ни в одной плохой строке — она отбрасывается, подсчитывается и протоколируется.
- Граничный хост не имеет собственной таблицы маршрутов.
- Типы внешнего интерфейса генерируются из Rust и никогда не пишутся вручную.
