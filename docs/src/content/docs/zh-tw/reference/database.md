三個儲存擴充套件點，彼此獨立選擇：**資料庫**、**cache**，以及可選的**檔案內容**。

## 資料庫

| `GPROXY_PERSISTENCE` | 連線 | 構建 |
| --- | --- | --- |
| `sqlite`（預設） | `<data-dir>/gproxy.db`，或 `--dsn` 裡的路徑 / `sqlite://` URL | 始終編譯在內 |
| `postgres` | `--dsn` 裡的 `postgres://…` | `--features postgres` |
| `mysql` | `--dsn` 裡的 `mysql://…` | `--features mysql` |
| D1 | Cloudflare binding | Workers 宿主 |
| libSQL / Turso | 經 Hrana HTTP pipeline | `--features libsql` |

MySQL 需要 8.0.13 或更新版本，以支援 JSON 列的預設表示式。PostgreSQL 和 MySQL 驅動均啟用 TLS 支援。

沒有 `--persistence` 時 `--dsn` 自己點明後端，所以通常 scheme 就夠了。

**本次構建沒有的後端會在啟動時被拒絕**，並指名能提供它的 feature，而不是等到第一個請求。

```sh
gproxy serve --dsn 'postgres://gproxy:…@db.internal:5432/gproxy'
```

libSQL 是給沒有 D1 的宿主——Deno、Netlify——準備的選項，因為 HTTP 那一段由呼叫方自己的
傳輸提供，因此它在每個目標上都能用。

### 一套 API 覆蓋全部

原生 SeaORM 連線與 Cloudflare D1 共享**同一套** store API。每個實體訪問器都走同一個泛型
倉儲，因此普通 CRUD 不用按表手寫，而且每個方法執行**一個原子批**。

構造 store 既不開啟資料庫，也不改動表結構。

兩個值得知道的推論：

- 讀取保持輸入順序、重複項，以及缺失 id 對應的 `None`，因此呼叫方可以把結果按請求拉回去對齊。
- 鍵謂詞會被拆分以適配 D1 的 100 個繫結值的語句上限，**而且仍在同一個批裡**。任意的呼叫方
  SQL 不會被拆，資料庫的請求與體積限制依然適用。

SQL 錯誤回滾事務性寫入。條件寫入影響 0 行時返回一個衝突，而不是把同一批裡的其餘部分回滾。
**沒有自動重試**：一個含糊的提交結果意味著先去核對持久狀態。

### 結構同步

```text
$ gproxy migrate --data-dir ./data
INFO gproxy::instance: schema is up to date warnings=0
```

同步是**以實體為先**的，不是一條編號的遷移階梯：一份登錄檔描述這些表，一次同步在新資料庫
上建立缺失的東西，在已有資料庫上增量新增受支援的缺失列與索引。重複呼叫保留資料。

`serve` 也會做這件事。單獨的命令是給那些把它當作獨立一步、**由單一寫入者**在任何實例啟動
前執行的部署用的——多實例共用一個資料庫正需要這樣。

同步**不做**的事：它不建立預設 settings 或管理員，不執行版本化遷移，也不轉換列的型別、
它的資料或已有的外來鍵。那些需要顯式遷移，而且不保證在每個原生後端上都是一個原子事務。

報告會帶上告警——例如 D1 的型別差異——而空列表**並不證明**每一項變更都被應用了。在認為
啟動完成之前，請先讀這些診斷。

## 精確金額

金額與限額以縮放後的整數存放，不是浮點。一個原子是 `0.000000001`，可表示範圍約為 ±92 億。

SQL 列是 `BIGINT`，而實體把這些原子以文字形式穿過 D1 的 JavaScript 邊界，好讓比較、排序
和加法在資料庫裡仍然是數值的。JSON 出於同樣的理由使用十進位制**字串**。

算術在一個 decimal 型別裡完成，並且**只**在整次結算上舍入一次，ties-to-even。結算在遞增
計數器之前會檢查負值與有符號溢位。

## Cache

| 後端 | 由什麼選擇 | 作用域 |
| --- | --- | --- |
| Memory（原生預設） | `--features memory` | 一個程序 |
| Redis / Valkey | `GPROXY_REDIS_URL` | 共享 |
| 資料庫 | wasm 上自動，別處可配置 | 經同一個資料庫共享 |

cache 裝 TTL 狀態、精確計數器、許可與租約，以及失效通知通道。它**不**裝業務實體，也**不**
裝持久賬本。

| 操作 | 語義 |
| --- | --- |
| `get` / `put` / `delete` | 不透明位元組、必填的正 TTL、每次 put 產生新版本 |
| `compare_exchange` | 期望的版本或不存在；替換或刪除 |
| `counter` / `increment` / `decrement` | 精確的非負整數，帶原子上限檢查 |
| `acquire_permit` | 最多 N 個存活持有者，各有自己的 TTL |
| `acquire_lease` | 同一個域、上限為 1——一把重新整理租約 |
| `publish` / `subscribe` | 有損的失效提示 |

操作**按 key** 原子，絕不跨 key。鍵值、計數器、許可和 topic 是分開的域，因此同一個邏輯
名字可以在每個域裡各自存在。

計數器有**固定視窗**：只有建立才確立 TTL，因此每個實例僅憑時鐘就能對邊界達成一致。許可
**不**按視窗計——它量的是在途請求，而任何邊界都不切分它——它的週期只是 cache 在從一個死掉
而沒釋放的請求那裡回收許可之前等多久。

### 故障是拒絕，絕不是本地回退

Redis 故障**不會**靜默降級到程序內 cache。兩個實例各自回退，會持有互相矛盾的鎖、把同一個
限額數兩遍，那比報錯更糟。

一個受限流的請求，若它的 cache 回答不了，就被**以 429 拒絕**。放行它會把一次 cache 故障
變成"這個實例上所有限額都關了"——那正是攻擊者想要而運維者看不見的時刻。

### 什麼時候需要共享 cache

跑多個實例需要 Redis，或者資料庫承載的 cache。沒有它，每個實例各數自己的限流、各自重新整理
同一個 OAuth 令牌，而且誰也看不見別人的配置失效通知。

登入會話也活在 cache 而不是程序裡，這正是 A 實例開始的登入 B 實例能收尾的原因——負載均衡
後面收尾的通常就是另一個實例。

對有多套環境的部署，給每套自己的 Redis namespace。通知 channel 顯式包含資料庫編號，
因為 Redis Pub/Sub 本身忽略 `SELECT`。

### 資料庫當 cache

對一個沒有常駐程序也沒有 Redis 的宿主——D1 或 libSQL 上的 edge isolate——cache 可以就是
資料庫裡的三張表。過期在 SQL 裡比較，因此同一個資料庫上的同伴對"什麼還活著"看法一致。

它**不帶通知傳輸**：訂閱會給出最初的 resync 提示然後什麼也沒有，因此這樣的宿主按自己的
節奏追趕。而那就是 Workers 宿主同步機制的全部：每個請求開頭讀一次 revision。

## 配置同步

```text
commit_revision([语句…, config_revision += 1, 读回])   一个事务
      ↓
reload   本实例的快照
      ↓
publish  ConfigurationChanged { revision, scopes }
```

兩套機制，缺一不可：

| | 傳遞什麼 | 會怎麼失敗 |
| --- | --- | --- |
| 共享 cache 上的失效通知 | 毫秒級的"再看一眼" | 丟訊息 |
| `settings.config_revision` 輪詢 | 持久事實，預設 30 秒 | 慢 |

通知從不攜帶狀態。它只說存在哪個 revision，而實例只在那個比自己正在服務的更靠前時才過載。
無法解析的載荷一律過載而不猜測。

**不能用 cache 自己的自增值代替資料庫的 revision。** Redis 重啟或淘汰可能丟失它，而兩次
獨立的提交——一次到資料庫、一次到 topic——不會因為捱得近就變成一個事務。

過載序列且單調推進：舊 revision 絕不覆蓋新的，過載失敗保留上一份快照繼續服務。

## 檔案儲存

可選，沒選後端就是關閉的。

| 後端 | 由什麼選擇 | 原生 | Workers |
| --- | --- | --- | --- |
| 本地檔案系統 | `--features fs` + `--file-storage-dir` | 是 | 否 |
| S3 相容，含 R2 | `--features s3` + `[file_storage]` 塊 | 是 | 是 |

它裝釋出出去的 body——`/publications/{id}` 背後的位元組——和下載的 tokenizer 詞表。
**檔案後設資料與歸屬留在資料庫裡**；儲存層只裝內容，別的什麼都不裝。

沒有配置檔案儲存時，釋出與詞表抓取回答"不支援"：沒有地方放這些位元組。

釋出連結還需要 `GPROXY_PUBLIC_BASE_URL`。沒有配置它時，釋出在任何 body 被寫入**之前**就
失敗，並告訴呼叫方改要內聯位元組。用請求的 `Host`——那是用戶端挑的——去拼連結會比沒有連結
更糟：上游的答案被接受、位元組被存下、URL 被交出去，然後它在別的地方 404。

## 備份

- **SQLite**——停掉程序並拷 `<data-dir>/gproxy.db`，或用 SQLite 自己的線上備份。
  **把主金鑰和副本放在一起**：一個加封的資料庫沒有它讀不了。
- **PostgreSQL 與 MySQL**——資料庫自己的匯出工具。
- **D1、libSQL / Turso**——平台自己的快照。
- **邏輯匯出**——`gproxy export --out config.json --include-secrets`。它帶走的是*配置*
  而不是歷史：身份、用量和 capture 刻意不在裡面。見
  [配置](/zh-tw/reference/configuration/#搬運一份配置)。

一份密文繫結到它那一行的 id，所以把某一行的金鑰恢復到另一行上是行不通的——這是一條安全
性質，不是整庫恢復的障礙。
