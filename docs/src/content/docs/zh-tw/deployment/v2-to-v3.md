---
title: 從 v2 SQLite 遷移到 v3
description: 使用 v3.0.22 升級 v2 SQLite 資料庫，了解遷移範圍與失敗後的還原方式。
---

原生 v3 服務會在開啟 v3 儲存前識別 v2 SQLite 資料庫。原有啟動命令可繼續使用 `--persistence db`、`--data-dir`、檔案型 `--dsn sqlite://PATH?mode=rwc` 和 `--update-channel staging`。如果來源資料庫已加密，保留原有 `GPROXY_MASTER_KEY`，不要同時輪換主金鑰。

## 升級前

- 保存目前的 v2 執行檔與啟動設定。v2 自動更新會替換執行檔，不保留舊版；v3 資料庫遷移無法找回已被替換的程式。
- 停止其他使用此資料庫的執行個體。原生入口會在存取資料庫前占用監聽連接埠，遷移還需要 SQLite 獨佔鎖。
- 預留完整來源備份、遷移工作資料庫和獨立切換快照所需的磁碟空間。
- 自動升級不支援 PostgreSQL、MySQL、遠端 libSQL、v1 資料庫或非標準 SQLite DSN。這些輸入需要先明確匯出、遷移。v2 PostgreSQL 到 v4 請使用[離線遷移工具](/zh-tw/deployment/v2-postgres-to-v4/)。

## 啟動時的處理

1. 取得遷移鎖，避免多個程序同時升級。
2. 在資料庫旁建立私有目錄 `gproxy-v2-backup-TIMESTAMP-PID`。
3. 獨佔鎖定 SQLite，執行 WAL checkpoint，再將來源複製為備份目錄中的 `gproxy-v2.db`。
4. 將支援的設定、可恢復的秘密、原始用量及上下游請求記錄匯入 `candidate/` 中的新 v3 資料庫。
5. 驗證匯入數量、SQLite 完整性、參照關係、執行階段控制狀態、用量筆數與精確的歷史結算費用總額。
6. 僅在驗證通過後寫入資料並原子替換設定所指向的資料庫。保留備份和 `report.txt`；重新啟動 v3 不會重複匯入。

組織、團隊與使用者的萬用路由授權（`*`）會保留。歷史用量只遷移仍在 `usages` 中的明細，v3 據此重建小時彙總。v2 用量彙總、每日憑證統計和歷史配額週期不會匯入，因此已被 v2 保留策略刪除明細的歷史不會出現在 v3 統計中；這些來源資料表仍保留在完整備份內。

憑證健康快照、tokenizer 快取與 Codex 工作繫結不會匯入。`report.txt` 會列出每個非空但略過的資料表、筆數與原因。未知資料表（即使非空）與 v2 限流規則也會略過並記錄。不支援的特定路由授權、未知權限範圍及主體已不存在的授權會略過；支援的萬用授權仍會匯入。略過的策略在 v3 不會生效，需要升級後重新設定。

`downstream_requests` 和 `upstream_requests` 分別遷入 `request_logs` 和 `wire_logs`。請求 ID、時間、方法、路徑或 URL、狀態、請求標頭及請求/回應本文會保留，包括同一請求的多次上游嘗試。v2 狀態碼 0 變為未知回應狀態。供應商與憑證參照會重新對應；已刪除物件使用停用的歷史預留物件。記錄以有界批次讀寫。

v2 特有的記錄建立/更新時間及每次嘗試的 `latency_ms` 沒有對應的 v3 欄位，仍保留在備份中；v3 從用量明細推導請求時長。稽核記錄不會匯入。瀏覽器與用戶端可能需要重新登入；可恢復的 API key 會保留。

## 失敗與還原

替換前失敗會保留原 v2 資料庫。檢查輸出中的工作目錄及資料庫旁的 `.gproxy-v2-upgrade-blocked`。這個標記避免程序管理器反覆複製失敗的資料庫而耗盡磁碟。修正原因後，只刪除這個標記再重試；不要透過刪除備份重試。

還原時停止 v3，保留目前的 v3 資料庫供調查，重新安裝已保存的 v2 執行檔或相同的官方版本，再將備份 `gproxy-v2.db` 還原到原資料庫路徑。還原前，將目前的 `-wal` 和 `-shm` 檔案隨目前資料庫一起移開。還原原啟動設定與主金鑰，再啟動 v2。不要讓 v2 開啟已遷移的 v3 資料庫。切換後寫入的用量留在保存的 v3 資料庫中，不會自動合併回 v2。
